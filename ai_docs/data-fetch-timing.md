この一覧は初回調査時点の記録。資産管理画面・再取込時の補完と失敗後の再試行については、後続の [asset-data-refresh-fix.md](asset-data-refresh-fix.md) を参照。

表示に必要なデータの取得漏れ・タイミング差は、追加調査 [data-fetch-gap-audit.md](data-fetch-gap-audit.md) を参照。

調査日: 2026-10-25（日本時間）。対象は `kurogane-dividend/android/` と `data/irbank/cloudflare/src/index.js`。HEAD `6231c90d` に作業ツリー上の未コミット変更を含めた静的調査であり、インストール済みアプリや本番の稼働コードとの一致、通信時刻・回数は未検証。

## 取得先と全体の流れ

アプリは起動時に端末の保存データを復元し、その後、必要なデータをHTTP APIから取得する。市場データはCloudflare Worker経由で取得し、WorkerがR2の公開済みデータやD1を読む。AndroidからD1へ直接SQLを実行する構成ではない。

| 取得先 | 主な内容 | 根拠 |
| --- | --- | --- |
| 端末内の保存領域 | 保有銘柄、ウォッチリスト、優待などは暗号化したSharedPreferencesとバックアップファイル。市場データは `cloudflare_market_cache` に保存 | `LocalImportStore.kt:24`、`DividendViewModel.kt:3070` |
| Worker → R2 | 銘柄検索、価格カタログ、銘柄情報、財務・配当、月末価格、分割履歴、空白月解消候補 | `CloudflareMarketRepository.kt` の各API呼び出し、Workerの対応ルート |
| Worker → D1とR2 | 銘柄分析はD1の `securities` を読み、R2のプロフィールなども使用 | `index.js:2485` の `/api/v1/analysis/{code}` |
| 外部為替API | USD/JPY。Frankfurterから取得 | `ServiceHttp.kt:56` |

以下の行番号は調査時点のもの。Androidのファイル名は `kurogane-dividend/android/app/src/main/java/com/kurogane/dividend/` 配下、Workerは `data/irbank/cloudflare/src/index.js` を指す。

## 通常の更新制限

`data/CloudflareMarketRepository.kt` の `PriceRefreshPolicy.shouldFetch()` は、原則として次の両条件を満たす場合に取得を許可する。

- 前回の取得試行日と、現在の日本時間の日付が異なる。
- 前回の取得試行から12時間以上経過している。

初回は取得できる。旧形式のキャッシュに前日の取得日だけがあり時刻がない場合は、正午まで待つ。たとえば10月25日20時に試行した場合、翌26日0時には取得できず、8時以降の取得処理の呼び出しで再判定する。時刻の到来だけで通信を開始するタイマーではない。

多くの処理は通信開始前に試行日時を保存するため、失敗しても同じ制限を受ける。制限中は保存済みデータを使用するが、キャッシュがなければ未取得・エラーになる。後述の強制再試行、年指定配当履歴、検索、通知用Workerなどは別の規則を持つ。

## 通常制限の例外とキャッシュ

- 財務の再試行ボタンは `force=true` で当日キャッシュと試行間隔を回避する。財務形式のバージョン移行にも通常制限を外す経路がある（ViewModel `:498`）。
- 財務一括更新では直近4暦年に欠けた配当履歴があると強制取得する。成功時に当日の補完試行済みを記録するため、失敗時は以後の呼び出しでも強制取得対象になり得る（`:664`）。
- 銘柄情報の会社情報メタデータ欠落、配当データ形式の移行、価格・利回りの形式移行には通常更新とは別の条件がある（`:2189,2451`）。
- 分析は通常の日次制限に加えて形式バージョンを判定する。取得不成立時は試行日時を消すため、次の呼び出しで再取得し得る（`:2271`）。
- 検索結果の価格等は `/live-quotes` を呼び、不足時に `/search-catalog` で補う。この補完用カタログにはRepositoryインスタンス内で5分のキャッシュがある。通常の価格一括更新とは別のキャッシュである（`CloudflareMarketRepository.kt:223,263,326`）。
- 年指定配当イベントは「当日の成功」と「30秒の試行間隔」で制御し、通常の12時間制限を使用しない（ViewModel `:927`）。

## アプリを閉じているときの取得

通知設定が有効な場合はWorkManagerが処理を予約する。以下は日本時間の初回実行目標で、朝・夕それぞれを24時間周期で登録する。ネットワーク状態やOSの制約で遅れるため、毎日その時刻ちょうどの通信を保証しない。

| 通知設定 | 取得タイミング | 取得内容・条件 |
| --- | --- | --- |
| 株価通知 | 8:30／17:30を目標 | 通知可能で、個別アラートが有効なウォッチリスト銘柄がある場合、価格カタログを取得 |
| 増減配通知 | 8:00／17:00を目標 | 保有・ウォッチリストの日本株の年次財務・配当を取得。Worker側は4文字コードに絞る |
| 配当通知 | 8:00／17:00を目標 | 正数保有の国内株・米国株の配当イベント・権利日情報を取得 |
| 配当・増減配の通知配信 | 8:30／17:30を目標 | 保存された通知用情報を処理する。この配信処理自体は市場データを取得しない |

配当通知を有効にしたときと、有効な状態でのアプリ起動時には権利日取得を単発予約する。増減配通知を有効にしたときと、有効な状態でのアプリ起動時にはViewModelが財務を強制取得する。端末再起動時は設定に応じて権利日・増減配取得を単発予約し、定期処理も登録する。

通知用Workerは画面用の `PriceRefreshPolicy` を通さずRepositoryを直接呼ぶ。画面用取得と同日に別途通信する可能性があり、通知用に取得した結果を画面の市場データキャッシュへ保存する処理も、これらのWorkerにはない。

根拠: `notifications/NotificationScheduler.kt:31`、`NotificationPolicy.kt:74`、`DividendNotificationWorker.kt:60`、`DividendChangeRefreshWorker.kt:22`、`DividendRightsRefreshWorker.kt:18`、`NotificationBootReceiver.kt:8`、ViewModel `:2989,3128`。

## 調査範囲と未確認事項

- Android本番ソースの取得関数と呼び出し元、キャッシュ条件、通知処理、対応するWorkerルートを照合した。`src/` の参照用アプリや `archive/` は現行Androidの根拠にしていない。
- サーバー側の収集ジョブがR2/D1を更新する時刻と、アプリの取得時刻は別である。サーバー更新後もアプリが再取得条件を満たすまで旧キャッシュを表示し得る。
- API名の `live-quotes` はリアルタイム更新の保証ではない。アプリ側の通信条件と、サーバーに格納されたデータの鮮度を区別する。
- Room／SQLiteの利用はAndroid本番ソースの検索で見当たらず、主要な端末データの実装は上記保存領域だった。Google Driveのバックアップ復元やファイル取込は、利用者が選択した別の入出力経路であり、市場データの定期取得には含めない。
- `fetchPopularStocks()`、`fetchPortfolioFinancialData()` は定義があるが、今回のAndroid本番ソース検索では呼び出し元を確認できなかった。定義だけを通常起動時の取得として数えていない。
- 実機・エミュレータの通信ログ、日付境界、失敗後の再試行、OSによるバックグラウンド遅延は未検証。アプリコード、既存の未コミット変更、本番データは変更していない。
