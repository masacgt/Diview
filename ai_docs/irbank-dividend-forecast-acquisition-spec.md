# IRBANK 配当・分配金予想取得仕様

更新日: 2026-11-02

状態: 取得方式の仕様。ガード付きキャッシュ再利用はコードに反映済み。新方式での実API呼び出し効率と全対象の取得結果は未確認。

## 目的と適用範囲

IRBANK Connect の開示書類APIから決算短信・配当予想修正等のXBRLを取得し、銘柄ごとの最新の有効な年間配当・分配金予想を `market/yfinance/v2/issuer_dividends/current.json` に保存する。取得元はIRBANKとし、J-Quants APIから予想値を補完しない。

定期処理は `irbank-v2-dividend-batch.yml` から `refresh_v2_dividend_batch.py` を実行し、実行ごとのAPI要求を最大200回に制限する。定期workflowは既定のWorker銘柄一覧を処理する。今回の調査用catch-up runnerは保存済み `--universe-json` を渡して最大20バッチを連続実行する。処理対象はその実行に渡された銘柄一覧とする。部分一覧を使う場合はその範囲だけを監査し、全体の `coverage_complete` を真にしない。今回の調査で固定した4,000件の一覧は次ページのカーソルを残しており、catch-up結果の適用範囲もその4,000件に限る。catch-up runnerは銘柄一覧の残りページを取得しない。

## API取得手順と上限

1. `/v1/usage` で残枠を読み、上限内で処理する。実行側はusage照会も200回の予算に含める保守的な計算を行う。
2. 銘柄ごとに `/v1/securities/{code}/disclosures` を開示日降順で取得する。検索期間は直近1,095日、1ページ100件とし、`next_cursor` をたどって最大10ページを読む。
3. タイトルが配当・分配金・決算・業績・運用状況等に該当する候補を開示日降順に並べる。候補書類のXBRL詳細は最大8件取得する。
4. 配当予想の処理は、一覧ページと詳細書類を合わせて最大18回の予約枠を確保してから始める。枠が不足する場合はその銘柄を未処理のままにし、次回位置を保存する。再試行も同じ予算管理に従う。

API処理はIRBANKのレート制限に合わせて間隔を空ける。日次上限、処理銘柄数、予想更新数、失敗数、次回開始コードを各バッチで記録する。

## 最新予想の判定

XBRLの現行期予想値から対象期、年間額、通貨・単位、株式1単位あたりの基準を読み取る。普通株の `DividendPerShare` とREIT等の `DistributionsPerUnit` を扱う。半年分の値を年間値として単純に採用せず、両期間が明示され、対象期間を確定できる場合だけ所定の計算を行う。株式分割による換算は、開示内容とIRBANKの実績調整係数で整合を確認できる場合に限る。

候補は新しい開示から順に詳細を確認する。新しい候補に有効な予想があればそれを採用する。新しい候補に予想値がなく、予想修正の関係も確認できた場合に限り、さらに古い候補へ進む。予想関連のXBRL項目が読めない、訂正書類の意味が確定できない、または書類詳細/XBRLを取得できない場合は、古い予想を最新と断定せず判定保留にする。

### 保存済み予想の再利用

保存済み予想には出典書類IDを保持する。開示一覧内に同じ出典IDがあり、そこへ到達するまでの新しい候補をすべて確認できた場合、次の条件を満たす予想に限って保存値を再利用できる。

- 対象期末が実行日より後である。
- 金額が現在の株式数基準で保存されている。
- 株式分割係数による追加換算を必要としない。
- その前に見つかった新しい候補が、有効な予想または要確認の訂正として残っていない。

新しい候補の書類が404、XBRL欠落、または詳細取得失敗となった場合は、キャッシュ値へフォールバックせず要確認または失敗として扱う。保存済み出典IDが一覧に見つからない場合もキャッシュを最新と断定しない。この条件により、キャッシュ書類が一覧にあるだけで採用する方式を避ける。

バッチはキャッシュ再利用数と、省略できた詳細API呼び出し数を記録する。安全条件付き方式の実測値が得られるまでは、以前の3銘柄試行で得た「平均5回」を本番の期待値として使わない。以前の試行は新しい候補を十分確認せずキャッシュを採用しており、楽観的な値だった。

## 結果状態とR2更新

`forecast_resolution` は少なくとも以下を区別する。

- `forecast_available`: 正の予想額を取得
- `explicit_zero_forecast`: 明示的なゼロ予想を取得
- `no_matching_disclosure`: 予想候補の開示なし
- `xbrl_missing`: 候補書類にXBRLなし
- `xbrl_item_missing`: XBRLはあるが対象予想項目なし
- `not_supported_by_disclosure_api`: 開示一覧APIの404等で対象外
- `review_required`: 訂正関係、対象期、単位、候補上限等で判定保留

通信失敗やAPIエラーでは、既存の有効な予想を消さずエラー状態と再試行日時を記録する。正常に確認できた開示に予想が見つからない場合は、旧予想を `previous_forecast` に残し、現行予想とは区別する。無配・明示ゼロは確認済みのゼロだけに設定し、未取得や開示なしをゼロにしない。

R2更新は既存インデックスを読み、対象レコードをマージして保存する。実績DPS、利回り、既存の対象外銘柄、その他の無関係なフィールドを維持する。部分一覧で新規登録した銘柄は追加し、一覧外の既存レコードも保持する。保存後に同じキーを読み戻し、SHA-256を照合する。

## 効果測定と運用上の留意点

1,866回の上限対象API呼び出しで339銘柄を確認した過去の平均は、約36.3銘柄／200回である。これは変更前の取得経路の実績であり、ガード付きキャッシュ方式の効果を示す数値ではない。新方式の運用時は、各バッチの処理銘柄数、API要求数、キャッシュ再利用数、詳細呼び出し削減数、予想取得数、状態別件数を分けて集計する。

部分一覧を使用した場合、監査結果には一覧のコードハッシュ、件数、カーソル残存の有無を記録する。部分一覧の対象範囲内で未処理がなくなっても、IRBANK全体の取得完了とは扱わない。
