# 表示に必要なデータと取得タイミングの不一致調査

本書は修正前の調査記録。後続の対応内容・検証結果は [asset-data-refresh-fix.md](asset-data-refresh-fix.md) を参照。

調査日: 2026-10-25。現行Androidの作業ツリーを対象に、資産管理、取込、銘柄詳細、ウォッチリスト、配当分析の表示側と取得側を照合した。調査中に別作業の変更・コミットが進んでおり、終了前のHEADは `708d165c`。以下は未コミット変更を含むコードの静的調査結果で、実機で起きた事象の再現結果ではない。今回、アプリコードは変更していない。

## 結論

保有銘柄を追加・取込した後に、資産管理画面で必要なデータがそろわない経路がある。新規保有には先読み処理があるものの、「取込の完了」と「表示用データの取得完了」は同期していない。また、既存銘柄の再取込、取得失敗後、ウォッチリストのみの追加には不足データを取得する契機が足りない。

取得処理を呼んだこと、通信に成功したこと、表示に必要な項目がそろったことは別である。現在はこれらを資産管理画面で判別するための状態がそろっていない。

## 資産管理画面が必要とするデータ

| 表示 | 必要なデータ | 現在の主な取得・反映経路 |
| --- | --- | --- |
| 評価額・損益・総資産 | 保有数量、取得単価、現在価格、米国株はUSD/JPY | 数量・取得単価は登録/取込。価格はカタログ・銘柄情報と端末キャッシュ。為替は起動時取得 |
| 配当利回り・年間配当 | 1株配当、株価または取得単価、数量、税設定、為替 | 価格/銘柄APIの配当値、条件付きで財務履歴から補完。設定と保有数量から計算 |
| 増配率・年額増減 | 連続する2年の財務配当履歴、数量、為替 | `_financialData` を監視。資産管理画面自体からの財務取得はない |
| 配当月・月フィルター・次回配当 | `dividendMonths` と配当・数量・為替 | 配当月API → `applyDividendMonths()`。月が空なら月フィルターから除外される |
| 名称・業種 | 銘柄情報、同梱の業種/名称マスター | 登録/取込時の値と `runtimeHolding()` による補正 |

根拠: `AssetManagementScreen.kt:258,868,878,1080,1216`、`DividendViewModel.kt:379,975,998,1030`、`Models.kt:32`。

## 確認した不一致

### 1. 取込完了時点では市場データの取得が終わっていない

`importCsvRows()` と `importDvmBackups()` は保有情報を保存して戻る。追加データの取得は `scheduleAddedHoldingDataFetch()` 内の別の `viewModelScope.launch` で動き、取込処理は完了を待たない。CSV画面は取込関数が正常に戻ると完了表示に切り替える。

さらに追加時の処理は、価格更新の終了を待ち、次に配当月取得の終了を待ってから、銘柄ごとの財務・分析・銘柄情報を取得する。先行する通信が遅いと、資産管理で使う増配率の取得開始も遅れる。大量取込では銘柄を8件ずつ処理するため、後続の表示項目はさらに遅れる。

影響: 初回取込直後に価格・配当・増配率・配当月が一部ずつ更新される。これは必ずしも恒久的な取得漏れではないが、取込完了をデータ準備完了とは扱えない。

根拠: `DividendViewModel.kt:1075,1091,1213,1226`、`CsvImportScreen.kt:263`。

### 2. 既存の正数保有銘柄を再取込しても、不足データの取得は開始されない

`updatePortfolio()` が取得対象とするのは、以前は正数保有しておらず、更新後に正数保有となったコードだけである。既存の正数保有銘柄の数量・取得単価をCSV/DVMで更新しても、財務・配当月・銘柄情報の取得は開始されない。取込結果が同一なら関数は先頭で戻る。

発生例: 最初の取込で財務・配当月取得が失敗し、通信復旧後に同じ銘柄のCSVを再取込する。既存銘柄なので先読みが呼ばれず、キャッシュがない項目は空のままになる。DVM取込も市場データキャッシュ自体を復元する処理ではないため、同じ条件になる。

資産管理画面は財務データを監視するだけで、自ら不足を検出して取得しない。銘柄詳細や配当分析には取得処理があるため、別画面への移動が取得の契機になる場合がある。ただし、後述の日次制限があると移動だけでは回復しない。

根拠: `DividendViewModel.kt:1075,1213,1226`、`AssetManagementScreen.kt:874`、`StockDetailScreen.kt:364`、`AnnualDividendScreen.kt:2457`。

### 3. キャッシュがなく取得に失敗した場合も、通常の更新制限がかかる

財務、配当月、月末価格、為替などは通信前に試行日時を記録する。失敗時にその日時を残す経路があり、「当日ではない、かつ12時間以上経過」の条件で次の取得を制限する。保存データがない状態でも制限される。

新規CSV/DVM取込は `forceNewHoldingData=false` の既定値を使う。手動の保有登録には財務・分析を強制取得する経路があるため、同じ銘柄でも登録方法によって回復条件が異なる。配当月には保有追加からの強制再試行引数がない。

影響: 一時的な通信失敗で「配当月未取得」や財務不足が当日中残り得る。月フィルターでは配当月が空の銘柄が表示対象から外れる。資産管理画面には、この取得をやり直す操作が見当たらない。

例外: 銘柄詳細の財務再試行、配当履歴不足の補完、形式移行には制限を外す経路がある。分析取得失敗時は試行日時を消す。したがって全APIが一律に12時間再試行できないという意味ではない。

根拠: `DividendViewModel.kt:498,664,872,1091,2271,2378`、`CloudflareMarketRepository.kt` の `PriceRefreshPolicy`、`AssetManagementScreen.kt:266`。

### 4. 財務不足を「増配率0%・年額増減0円」と表示する

資産管理の増配率は連続する2年分の財務配当履歴が必要だが、その組がない場合も `0.0%`、`年額 ¥0` を表示する。履歴未取得、取得中、取得失敗、比較不能を「変化なし」と見分けられない。

取得成功後はStateFlow経由で再描画されるため、画面が一度表示されたら更新されないという問題ではない。問題は、取得前・失敗時・必要年数不足の表示状態と、画面からの取得契機が不足している点にある。

年間配当にも未取得時に0が計算へ入る経路があるが、これは現在のデータ契約で未取得と無配確定を別フラグにしている。計算上の0を無配確定と読み替えたり、古い配当を無条件に復活させたりする修正は適切でない。

根拠: `AssetManagementScreen.kt:878,1084`、`data/MarketDataContract.kt`。

### 5. 為替取得は起動時のみで、米国株追加・通信復旧ではやり直さない

`refreshExchangeRate()` の本番呼び出し元はViewModel初期化処理のみ。米国株を追加・取込する処理と資産管理画面には呼び出しがない。起動時に失敗してキャッシュもない場合、後から米国株を追加しても為替不足が残る。

`Holding.currencyFactor` は為替がない米国株では0になり、円換算評価額・取得総額・年間配当の集計へ0が入る。資産管理画面には為替不足の警告はあるが、そこで再取得する処理はない。通常の再起動でも、同日の失敗日時による制限を受け得る。

根拠: `DividendViewModel.kt:473,1091,3139`、`Models.kt:35`、`AssetManagementScreen.kt:423`。

### 6. ウォッチリストのみの追加・DVM復元は、配当月・財務の取得を開始しない

`registerWatchlistStock()` は必要なら銘柄情報を解決するが、`addHoldingToWatchlist()` は保存と既存配当月キャッシュの適用だけである。DVMでウォッチリストを復元する経路にも、復元したコードを対象とする配当月・財務の取得呼び出しはない。保有銘柄も新規追加された場合は、その保有向け取得が同じコードを補うことはある。

銘柄解決で財務取得するのは年間配当が正でない場合だけなので、年間配当がある銘柄の過去財務が同時にそろう保証もない。ウォッチリストの配当予測・配当リスク表示は保存済みの月/財務を使用し、表示時に不足分を取得する処理は見当たらない。

発生例: 起動時の一括取得が終わった後、未保有・未キャッシュの銘柄をウォッチリストだけに追加する。年間配当が分かっていても配当月や配当リスク判定用財務が欠け、詳細表示や次回起動等が必要になり得る。

根拠: `DividendViewModel.kt:1226,2253,2817,2833`、`WatchlistScreen.kt:463,2903`。

### 7. 米国株・投資信託の増配率には、資産管理が要求する取得経路がない

保有追加時と通常の財務一括更新は `Category.JAPAN` を対象とし、銘柄詳細も日本株以外の財務取得を実行しない。一方、資産管理の増配率表示は全カテゴリで同じ財務配当履歴を参照する。

そのため米国株・投資信託には、待てば財務履歴が届くという前提を置けない。配当月APIのイベントは別の保存先であり、その取得だけでは資産管理の増配率に使う `_financialData` は埋まらない。これはタイミング調整だけでなく、対象外表示またはカテゴリ別データ経路の判断が必要な不一致である。

根拠: `DividendViewModel.kt:664,1114`、`StockDetailScreen.kt:365`、`AssetManagementScreen.kt:874`。

### 8. 空白月解消候補は起動時失敗後、利用画面で再取得しない

候補一覧の取得関数は起動時のみ呼ばれる。ウォッチリスト側はキャッシュとエラー状態を表示するが、利用時の再取得は呼ばない。起動時にネットワークがなくキャッシュもない場合、通信復旧後に候補画面を開いても不足したままになる。再起動時も日次・12時間制限が適用される。

根拠: `DividendViewModel.kt:757,3137`、`WatchlistScreen.kt:334,480,2843`。

## 関連する表示・取得条件の差

- CSVから取り込んだ現在価格より、`runtimeHolding()` は端末の価格キャッシュを優先する。既存保有の再取込では価格取得が開始されないため、新しいCSV価格を入れても古いキャッシュが使われる条件がある。これは未取得ではなく、更新日時を比較せず取得元を優先している問題。根拠: `PortfolioImporter.kt:36`、`DividendViewModel.kt:389,1085,2451`。
- 配当分析の月次資産推移は `[A-Z0-9]{4}0?` に合うコードだけを取得対象にする。一方、Repositoryは独立した5文字コードにも対応しており、末尾0でない5文字コードは月次画面側で除外される。該当コードを保有する場合は、待機や再試行では取得されない。根拠: `AnnualDividendScreen.kt:3368`、`MarketDataContract.kt:5`、ViewModel `loadMonthlyPriceHistory()`。
- 月次価格、年指定配当イベント、分割履歴を利用画面で取得する設計自体は取得漏れではない。実際にその表示が必要になった時点で取得を開始し、取得中・失敗・元データなしを区別できるかを評価する必要がある。

## 修正を検討する順序（未実装）

1. 資産管理で使う必須データの状態を、未取得・取得中・成功・元データなし・失敗に分ける。増配率の比較不能を変化なしと混同しない。
2. 新規保有だけでなく、再取込した既存銘柄・復元したウォッチリストについても、不足項目を判定して取得する。既存キャッシュが十分なら不要な通信は避ける。
3. 初回取得失敗の再試行と、正常キャッシュの鮮度更新を別の制限にする。通信復旧・再試行操作・利用画面表示で回復できるようにする。
4. 為替など複数画面で使う共通データにも不足時の再取得経路を設ける。米国株等の対象外項目と5文字コードの対象条件を整理する。
