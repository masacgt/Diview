# Trouble

- The legacy `/api/v1/monthly-price-history` path divided yfinance `Close` values by later split ratios even though Yahoo Finance had already split-adjusted those closes. A production Worker hotfix now returns the stored close unchanged; the live API matched saved yfinance closes for five split and five reverse-split samples. The repository's v2 path also reads `Close` without another adjustment, while the first v2 R2 publication and full v2 Worker deployment remain pending.
- On 2026-10-15, production `/api/v1/securities/8783` returned a legacy IRBANK fiscal-year 2010 `annual_dps_adjusted` of 16.67 and a yfinance quote dated 2026-10-07, while `/api/v1/search-catalog` had a quote dated 2026-10-09. Android had treated the fiscal DPS as current and preferred the older per-security close, producing 37.88% yield from obsolete inputs. The repository now accepts DPS only from the v2 current payload/catalog and selects the later quote date. Apply the change to the production path only after v2 R2 publication and Worker deployment; the production split-history route was still 404 during this audit.
- A previous 15+15 split audit added issuer-side numeric overrides to five IRBANK rows. Those values were not yfinance event values, and the 7161 annual total was explicitly not company-reported because pre- and post-10:1 consolidation amounts could not be added directly. The local canonical JSON and D1 input were restored to their prior values; the remote legacy R2 objects were not read back or rewritten. The app's yfinance chart path now excludes those issuer totals. Until v2 publication and Worker deployment complete, production may still expose legacy values through old routes.
- Root cause for the mismatch: `annual_dps_adjusted` is a rebased fiscal-year aggregate, not a sequence of dated cash distributions. A year containing dividends before and after a split or consolidation mixes per-share units; multiplying or dividing the annual total once cannot reconstruct each event. Yahoo/yfinance can also return event amounts with different historical share-basis treatment across symbols. Therefore the durable path stores yfinance's repaired daily event amounts, sums by event date for calendar-year and trailing-12-month views, and does not independently reapply split ratios. Those sums are clearly identified as yfinance calendar-year distributions, not issuer-reported fiscal-year DPS.
- The v2 collector previously read `ticker.dividends`/`ticker.splits` with `repair=False`, then merged all prior dates. That could retain old duplicate or wrong amounts after Yahoo corrected an event. yfinance 1.7.0's `repair=True` path uses SciPy for unit-mixup detection and scikit-learn DBSCAN during damaged-price reconstruction. In the representative audit, history calls failed with `ModuleNotFoundError: sklearn` when scikit-learn was absent, so `scikit-learn==1.9.1` is now pinned beside yfinance 1.7.0 and SciPy 1.18.1. The collector surfaces yfinance exceptions to its per-security retry state machine, fetches full daily action history, replaces events within the returned coverage, preserves previous data only on fetch failure, and records the amount basis and library versions. The Worker no longer substitutes IRBANK DPS into the yfinance calendar-year graph. The audit also found three reverse-split cases with inconsistent event share bases; see the open normalization item in `todo.md`. Production R2 and Worker still need a successful refresh/deploy before these changes are live.
- Wrangler can fail with `Invalid access token [code: 9109]` when a stale `CLOUDFLARE_API_TOKEN` environment variable overrides an existing Wrangler OAuth session. Remove that variable only from the current PowerShell process before invoking Wrangler; `wrangler whoami` then confirms whether the saved browser OAuth session works. Do not print or paste token values.
- The first weekend capacity benchmark used `datetime.now(JST).date()` instead of the latest completed XTKS session. As a result, the quote check targeted Saturday 2026-10-17 and failed for all 20 securities and 495/500 securities in the larger samples; the workflow passed because it only treated HTTP 429 as a job failure. `benchmark_v2.py` now uses `latest_completed_xtks_session`, reports core quote/profile success rate, and fails above a 10% core failure rate. A weekend-session regression test was added; a valid rerun is still required.
