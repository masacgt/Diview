## 取得元から表示まで

```text
J-Quants（銘柄一覧・商品区分） ─┐
Yahoo Finance / yfinance ───────┼─ 同期処理 → Cloudflare R2 ─┐
IRBANK Connect API ─────────────┘                            ├→ Worker API → Android
                                            Cloudflare D1 ───┘        ↓
                                                         端末内の保存・キャッシュ → 画面
```

Androidは市場データを主にWorker APIから取得する。Workerは用途に応じてR2の市場・財務データやD1の情報を読む。AndroidがD1を直接操作する構成ではない。保有銘柄、保有数量、取得単価、口座区分、ウォッチリスト、利用者が入力した情報は端末側の保存データから復元する。起動のたびに証券会社の口座から自動取得する処理ではない。為替など、上図と異なる外部取得経路もある。

| データ | 主な取得元・保存先 | 意味 |
| --- | --- | --- |
| 銘柄対象・商品区分 | J-Quantsの銘柄一覧をR2に保存 | 日本株、ETF、REITを対象に含め、商品区分を保持する。全銘柄の全項目を取得できる保証ではない。 |
| 価格・配当イベント・財務情報の一部 | Yahoo Financeをyfinance経由で取得してR2に保存 | 価格日、配当イベント日、財務期間などを区別する。アプリからの取得時刻と取得元のデータ時点は別。 |
| 発行体の配当実績・予想 | IRBANK Connect APIと開示資料を取得処理で読み、R2へ保存 | 配当実績APIは実績が対象。予想は別途開示資料から取得を試みる。暦年イベント合計と決算期の配当は別系列。 |
| 銘柄区分の画面表示 | R2のJ-Quants商品区分 → `/api/v1/security-categories` | 日本株の業種が未分類の場合、`013`をREIT、`014`をETFとして資産管理画面に補足する。保有データ自体の業種は変更しない。 |

銘柄一覧に載ることと、ある取得元で価格、配当、財務のすべてが取得できることは同義ではない。2026-10-27の限定的な直接照会では、IRBANKの銘柄一覧に載るREIT 8953・8951・8984とETF 2084・1591・1546は、配当履歴で対象なしとなった。株式7203・8316は配当履歴を取得でき、6721は正常応答で履歴が空だった。これはサンプルの結果であり、REIT・ETF全体の対象外を証明するものではない。

## 起動・画面操作と更新条件

通常起動では、保有情報や保存済みの市場・財務データを端末から復元し、保存値を画面へ反映する。その後、更新条件を満たす場合に保有銘柄の価格、銘柄情報、財務、配当イベントなどを取得する。ウォッチリストや米国株の有無、通知設定によって追加処理がある。時刻になっただけで通信するタイマーではなく、起動や画面操作などの取得契機で条件を判定する。

| 対象・契機 | 条件・動作 |
| --- | --- |
| 起動時の一括更新 | 原則、日本時間の前回試行日と今日が異なり、前回試行から12時間以上経過している場合に開始。初回は取得可能。前日の日付しか残らない旧キャッシュは正午まで待つ。 |
| 価格、銘柄、財務、配当イベントなど | 一括更新に加え、対象データごとに取得日時・キャッシュ等を確認する。したがって一括更新が始まっても、全項目が必ず通信されるわけではない。 |
| 取得失敗 | `MarketFetchPolicy` を使う処理は、失敗から30秒後以降の次の取得契機で再試行可能。起動一括処理など別の制限が先に働く場合もある。30秒後の自動実行を意味しない。 |
| 財務 | 日次キャッシュと試行状態を使用し、更新契機にはサーバーの改訂情報やデータ形式も判定する。明示的な強制取得は通常のキャッシュ制限を回避する。 |
| 資産管理の商品区分 | 画面表示時や保有追加時に、対象となる未分類の日本株について確認する。成功した銘柄別キャッシュは45日間使い、未取得や期限切れは取得対象になる。 |
| 銘柄詳細 | 銘柄情報、財務、分析、配当イベントなどを必要に応じて取得する。配当イベントは年指定に対応し、旧Worker向けには単年取得へフォールバックする。 |
| 検索・通知 | 起動時一括更新とは別の取得契機を持つ。通知は設定やスケジュールに従い動作するため、起動条件だけで全通信を説明できない。 |

実機で2026-10-27に読み取った記録では、起動一括処理の前回試行は13:20、8953の財務取得試行は22:59、商品区分の取得は22:34だった。これらは各確認時点の記録であり、今後の取得成功や毎回の通信有無を示すものではない。実際に再起動して通信を観測する試験は、この確認では行っていない。

## 取得効率化後の動作

元の調査では取得重複や画面・通知間の参照元の違いが見つかった。表示内容を変えない範囲の改善として、次を実装した。

1. Workerの1リクエスト内、または1銘柄の定期分析内で、重複する小さいR2文書の読み取りを共有する。共有結果は利用側ごとに分離し、失敗時は再試行できる。別リクエストへ結果を保持する新しい鮮度期間は設けない。
2. Androidの通常Repositoryは、同時進行中の同一URL・同一キャッシュ指定のHTTP読み取りを共有する。完了または失敗後は共有対象から外し、後の更新や明示的な再試行を妨げない。
3. 明示的に取得した全銘柄カタログを既存の検索・詳細補完用5分キャッシュへ反映する。明示的な全件更新自体を省略する仕様ではない。
4. `include_history_bounds=false` 指定時は、非表示の配当履歴の開始・終了範囲を求める走査を省く。配当イベント、価格、予想等を変更するための指定ではない。
5. 月次価格は参加銘柄のいずれにも更新が必要ない月を一括要求から除き、保存済みデータを利用する。

これらは異なる意味の配当系列や更新条件を統合する変更ではない。改善時の検証では、模擬データで分析APIのR2 GETが11回から7回となり、比較した応答は一致した。実機・エミュレータ各33枚の画像はそれぞれの変更前と一致したが、独立したテストデータでの結果であり、全実銘柄の表示一致や本番の通信削減率を保証するものではない。公開後の本番応答比較と実機の限定的な通信確認も実施済みで、詳細は [改善記録](https://github.com/masacgt/Diview/blob/9a914582/ai_docs/data-fetch-efficiency-implementation-20261027.md) と [main統合記録](https://github.com/masacgt/Diview/blob/9a914582/ai_docs/fetch-efficiency-main-integration-20261027.md) を参照する。

## 配当・分配金の選択と表示

発行体の決算期実績、発行体の予想、Yahooの暦年イベント合計、アプリの年間推計は、同じ金額であっても出典と対象期間が異なる。銘柄詳細の上部と保有銘柄の年間配当推計には、条件を満たす発行体予想、イベントからの推計、Yahooの1株当たり予想年間配当額の順に利用可能な値を選ぶ処理がある。イベント推計には次回イベントが必要で、現在年の観測済みイベントと次回権利日を使う。発行体が公表した将来予想を意味するわけではない。

IRBANK取得処理は、配当実績の正常応答に履歴がなければ `empty` として保存する。また、現行処理では配当履歴APIのHTTP 404も `empty` に変換する。Workerは有効な発行体予想や実績が優先されない場合、この `empty` を年間0円・無配として返す。ユーザーが指定した「正常に取得した空配列は無配と判定する」ルールと、HTTP 404を空配列と同じ状態にする現在の実装は区別して理解する。404から実際の無配は証明できない。

2026-10-27の8953の確認では、発行体は2026年2月期3,006円、同年8月期3,012円の分配金を公表し、アプリは該当する観測イベントの合計6,018円を年間推計に使用していた。一方、当時の銘柄APIはIRBANKの `empty` に基づく0円・無配を返していた。この食い違いは取得効率化前後の両方で観測されており、同改善が生じさせたとは確認されていない。金額は1口当たりの時点例であって、将来予想ではない。 [発行体の分配金情報](https://www.jmf-reit.com/ir/distribution.html)

資産管理の「直近増配」は利用可能な連続する年の配当履歴を比較する。2026-10-27の8953の表示では、2024年4,576円と2025年5,628円の比較に基づく約23.0%であり、同画面の2026年イベントを用いた年間推計とは基準期間が異なる。REITの数量について、当時の資産管理画面は共通の「株」表記を使っていた。

## 未解決事項と確認の限界

- IRBANKの404と正常な空配列が同じ `empty` となるため、分配金がある銘柄をAPIが無配と返す場合がある。取得対象なし・取得失敗・正常な空配列・明示的な0の扱いをどう変更するかは未決定。Yahooの補助利用は提案であり、実装済み仕様ではない。
- 画面と通知の価格・利回りの選択、通知と画面の永続キャッシュ共有、財務APIと分析APIの応答統合、履歴更新の世代管理、フォールバック経路の統合は、この効率化で解決したとは扱わない。
- 起動・画面・通知・サーバー同期では取得条件が異なる。全銘柄の鮮度や、本番の通信削減率、起動速度の改善幅は測定済みとしない。
- 上記の実機保有データの登録経緯は不明。取得処理だけから、ユーザーが登録したか、別の操作で生じたかは断定できない。
