# yfinance v2 market data

The `yfinance-r2.yml` workflow is the scheduled collector. It starts at 21:17 Japan time on weekdays, checks the XTKS exchange calendar, obtains the current listed-security universe from J-Quants v2, and writes app-required yfinance data to `market/yfinance/v2/` in the private `diview-market-data` R2 bucket. It uses the standard GitHub-hosted Ubuntu runner; standard runners are free for public repositories.

The J-Quants master includes equities, ETFs, and REITs. Its product category is retained in the v2 universe, while the app continues to resolve industry names through its bundled industry master. Each J-Quants code is converted to a Yahoo Finance `.T` symbol. A security enters the search catalog only after its yfinance profile and completed daily close are available.

The collector pins `yfinance==1.7.0`, `scipy==1.18.1`, and `scikit-learn==1.9.1` so scheduled runs do not silently change price-repair or dividend-event behavior when a library release appears. yfinance's `repair=True` path uses SciPy for random unit-mixup detection and scikit-learn's DBSCAN when reconstructing damaged price intervals; without scikit-learn, some history requests fail before actions can be stored. Upgrade these dependencies deliberately and validate representative split, reverse-split, and ordinary dividend histories before publishing a new collector version. Rights-date calculation uses the separate `requirements-rights.txt` set (`exchange_calendars` and `boto3`) and does not install yfinance, SciPy, or scikit-learn.

Manual workflow mode `split-audit` performs a read-only comparison for current securities with split or reverse-split events in the latest eight years. It reads dated yfinance event partitions from R2 and compares their fiscal-period sums with the processed issuer `annual_dps_adjusted` snapshot, using each reported fiscal-period end date to assign events. It writes per-security and per-fiscal-year CSV files plus a summary artifact; it never writes to R2 or changes the app's yfinance-only data path. Missing issuer DPS, missing fiscal dates, failed yfinance history, and numerical mismatches remain separate outcomes. A mismatch identifies a case for source-level review; it does not by itself establish which source is wrong. The full-universe audit in [Actions run #58](https://github.com/masacgt/Diview/actions/runs/39000622938) covered 1,068 securities and 1,271 split events with zero technical failures. It compared 7,345 issuer fiscal years: 6,206 were within ¥0.05 per share and 1,139 exceeded the tolerance; 160 securities had no issuer DPS snapshot. This is a review report, not proof that either source is wrong.

## Published data

- `manifest.json`, `universe/current.json`, `catalog/current.json`, generation snapshots, and `publications/current.json` describe the active universe and publication state.
- `securities/{symbol}/profile.json` contains security identifiers and the Japanese-locale display-name fallback fields. Exchange, country, business summary, market capitalization, and profile-level shares outstanding are not retained; J-Quants supplies the supported market universe and product category. Currency is stored with the current quote.
- `securities/{symbol}/current.json` contains the latest completed close and date, trailing 12-month dividends, Yahoo's `dividendRate` estimate for the next 12 months, current-fiscal-year dividend events observed through the collection date, yield, PER/PBR, and per-field retrieval state. `dividendRate` is not an issuer-confirmed next-fiscal-year DPS.
- The collector stores an upcoming ex-dividend date from `Ticker.calendar` when that field is due for refresh; the Worker falls back to `statistics.exDividendDate` from `Ticker.get_info` when no calendar date is stored. The API labels the selected source and status. The Android Stock Detail screen requests `/api/v1/dividend-months` for the viewed security once per JST date; empty upcoming-event data displays as unavailable, while request failures preserve cached values and remain eligible for retry.
- `securities/{symbol}/prices/monthly/{year}.json` contains the latest eight completed December `Close` values (including the newest point); older points within the eight-year window remain under `archive/prices/monthly/{symbol}/{year}.json`.
- Each December price point's `date` is the final XTKS session of that December; the yfinance monthly candle timestamp is not used as the close date. Manual workflow mode `repair-monthly-prices` normalizes dates in existing R2 partitions, verifies each rewritten object, and makes no Yahoo/yfinance requests. The scheduled writer applies the same normalization when it next touches a security.
- `securities/{symbol}/dividends/{year}.json` and `splits/{year}.json` contain the recent ten years of events. Older events move to `archive/events/{symbol}/{dividends|splits}/{year}.json` and are retained indefinitely. The daily one-year price chart also supplies unrepaired dividend/split candidates for change detection; these candidates never replace stored repaired events. When an event is new or changed, the collector fetches the affected coverage again with `history(actions=True, repair=True)` and replaces the successful range. Complete repaired history is rechecked in one of 20 rotating groups, about once per month, and immediately when a newly detected split requires a complete refresh. Event amounts are stored as returned after yfinance repair, with no second split-ratio adjustment in this pipeline. A failed fetch keeps previous events and records a retry state.
- The financial-data history chart sums yfinance-repaired distribution events by calendar year. It does not present IRBANK's adjusted fiscal-year DPS as an observed yfinance distribution or company-reported calendar-year total. Calendar-year sums can differ from issuer fiscal-year DPS, and the event share basis is not independently normalized. `current.json` records the action-history coverage, yfinance version, amount basis, and repair mode.
- App-required annual financial inputs are stored in `securities/{symbol}/financials/{period-end}.json`, using the full `YYYY-MM-DD` reporting date so distinct fiscal periods that end in the same calendar year remain separate. Existing `YYYY.json` partitions are still read and updated when they already contain the exact period. The records contain sales and operating income, stockholders' equity and total assets, operating and investing cash flow, plus yearly EPS, book value, and dividend yield. The yfinance cash-flow rows `CommonStockDividendPaid` and `CashDividendsPaid` are also retained. When a matching annual record contains a positive `StockholdersEquity` and a cash-dividend-paid value, `calculated_doe` is computed as the absolute dividend cash outflow divided by fiscal-period-end stockholders' equity, times 100. Common-stock dividends are preferred; total cash dividends are used only if that row is absent. The source field, formula, and per-field state are stored with the annual record. The calculation uses yfinance reported cash flow for the fiscal period and is distinct from an issuer-published DOE. For net D/E, the collector prefers yfinance `NetDebt`; if absent, it calculates total debt less cash and short-term investments (or cash and cash equivalents) for that same period. It divides net debt by positive `StockholdersEquity`, falling back to total equity including minority interests; incomplete inputs or non-positive equity leave the ratio unavailable. The source fields, formula, and field state are stored with the annual record. Policy version 2 schedules existing securities through the rotating five-group initialization so the new value is collected before the normal fiscal-marker or 45-day refresh. Unused statement rows such as net income, statement EPS, shares outstanding, and capital expenditure are not retained. `sync.json` records attempts, last success, retry count, per-field state, and failure reason.

### One-time migration of existing financial values

The manual Actions mode `migrate-financials` copies the app-used annual fields from existing `market/irbank/v1/securities/{code}/overview.json` objects into `market/yfinance/v2/securities/{symbol}/financials/{period-end}.json`. Full period-end keys allow legacy and yfinance records with different fiscal year ends in the same calendar year to coexist. It marks copied fields as `legacy_migrated`, retains their values and IRBANK source reference under `annual.source_values.seed` or `valuation.source_values.seed`, and reads every changed object back before reporting success. It does not fetch Yahoo data or delete the source objects. The collector records later Yahoo values separately under `source_values.yfinance`; the flat values used by the existing app contract prefer yfinance when present, while the seed remains available. Derived metrics identify calculation inputs and their source category. The Worker also exposes retained seed records separately as `financials.seed_annual` and `valuation.seed_history`, and keeps the existing annual/history fields for app compatibility. Older flat v2 records are classified from their field status and migration marker when the source-specific object is first updated. Run the migration successfully before deploying the Worker version that no longer falls back to legacy financial data.

The manual Actions mode `migrate-irbank-dividends` copies legacy issuer-reported fiscal-year dividend rows into `market/yfinance/v2/securities/{symbol}/issuer_dividends/{fiscal-year}.json`. It reads `market/irbank/v1/securities/{code}/dividends.json` first and falls back to `market/securities/v1/{code}.json`; each row keeps its fiscal-year values, source references, and attribution. Existing v2 fiscal-year rows are preserved, every inserted row is read back, and source objects and dated yfinance event partitions are not changed. The Worker financial-data response returns these issuer records separately from its calendar-year yfinance event totals. This migration does not infer event dates or convert fiscal-year DPS into calendar-year distributions; issuer records are retained as seed data while future yfinance event records are added separately.
- Calculated XTKS rights-date data is published at `derived/rights_dates/current.json`. The calculation consumes only v2 event and current-data objects.
- The first `derived/income_advice/current.json` publication is a separate R2-only reaggregation. Run the manual `generate-income-advice` workflow mode to read the published V2 catalog, current/statistics documents, latest annual financial rows, and the last three completed calendar years of dividend events; it computes eligible candidates, writes the derived object, and verifies the R2 read-back. It makes no Yahoo or J-Quants requests. Normal V2 catalog syncs refresh this derived object as part of their publication.
- Unused fields from a legacy yfinance security object are compressed under `archive/legacy/securities/{symbol}/unused.json.gz` and retained for ten years. The source object is removed only after the v2 data and archive have been read back and checked.

## Collection and publication behavior

The market calendar skips weekends and Japanese exchange holidays. Each trading day, all active securities refresh yfinance company/current statistics and one `history(period="1y", interval="1d", actions=True)` chart. The same response supplies the exact-session `Close` and latest-year dividend/split candidates, removing the former separate quote and actions requests. Only the current quote and event records are stored; the other daily rows are discarded. A missing same-session close fails that security's attempt, keeps the prior published close, and records a retry; a previous day's close is never relabeled as today's. Normal event comparisons read the latest three calendar-year partitions, enough for trailing-12-month and current-fiscal-year calculations. Unchanged daily candidates do not rewrite historical event partitions; migration, changed events, or full-history repairs update the affected event data. Full action history and the initial eight completed December closes are spread across 20 persistent rotating groups; this gives a roughly one-month first-pass/refresh cycle. A newly detected split or reverse split triggers a full action-history refresh and a fresh yfinance fetch of all eight December closes for that security, replacing the stored split-adjusted prices. Annual financial statements and valuation measures refresh when Yahoo's `lastFiscalYearEnd` or `mostRecentQuarter` marker changes, at the one-time five-group initialization pass, or after 45 days without a check. A retry fetches only financial groups previously marked failed. Same-session retries after a partial result reuse successful profile, close, action, and financial groups; required daily market fields still refresh on the next market session. December closes are refreshed for all securities after the last Tokyo trading session in December. Each ticker is attempted at most four times per market day across repeated workflow executions. Empty dividend/split histories remain distinct from failures. Yahoo `YFPricesMissingError` and HTTP 404 are stored as `no_data` and are not retried again during the same market session; they are reconsidered on the next session. HTTP 408/425/429/5xx and timeout/connection errors are classified as transient and remain retryable within the four-attempt daily cap. Other exceptions are marked `unknown` for diagnosis.

The publication record and Actions log include elapsed synchronization seconds, per-phase timings, R2 request counts and timings, and counts of high-level yfinance requests by method. During per-security collection, the publication also records the union of yfinance-request and R2-request active wall time, their overlap, and the yfinance-only, R2-only, and idle portions. These intervals distinguish time spent waiting on each service from worker count alone; they do not include Actions setup, dependency installation, J-Quants retrieval, or catalog publication. The monthly scheduled-run target is at most 2,000 GitHub-hosted runner minutes; repeated normal-session runs are required to confirm it. The workflow runs deterministic Python sync tests on relevant pushes and pull requests. Its manual `run_mode` choices include `refresh-financials`, which refreshes one ticker's annual financial records and verifies their V2 read-back without rebuilding the full-universe catalog. Other modes include `test`, `benchmark`, `sync`, `migrate-financials`, `reaggregate-dividend-streaks`, `repair-monthly-prices`, and `split-audit`. The benchmark uses a J-Quants sample and makes no R2 writes. It compares unrepaired daily-chart action candidates with repaired history for every sampled security and reports response counts, decoded response-body bytes, event counts, and fingerprints. A separate per-symbol JSON artifact retains event rows and comparison errors. For a 500-security sample, the selector prioritizes all recent split/reverse-split codes present in the J-Quants universe. The existing split-event catalog is used only to choose a representative sample; it is not used as event data or as the comparison's expected values. Repaired history remains authoritative when a candidate indicates a change.

Manual `benchmark` runs accept 16 or 24 ticker workers while keeping the HTTP request-start limit at 8 per second. A push whose commit message contains `[yfinance-capacity-study]` runs a sequential, non-publishing comparison of 20 securities at 16 workers, 500 securities at 16 workers, and 500 securities at 24 workers; summary logs and per-symbol JSON reports are saved as a 30-day workflow artifact. The benchmark probes 7203.T and uses the earlier of its latest available close and the latest completed XTKS session, reporting both dates, profile success, exact-close availability, and total benchmark time. Production sync still requires the exact latest completed XTKS close. The benchmark fails on any HTTP 429, profile failure above 10%, or exact-close availability below 50%; individual securities without a close are listed in the report. This marker is intended for a deliberate capacity measurement because it consumes Actions time and makes Yahoo requests.

A push whose commit message contains `[yfinance-full-universe-study]` runs and publishes the full J-Quants universe to R2 with 24 workers and the same 8-requests-per-second limit. The study forces a full-universe pass, but same-session retry handling reuses successful profile, close, action, and financial fields for securities already completed in that market session. It therefore measures the R2/catalog path and is not a fresh daily yfinance acquisition measurement. This manual mode bypasses the weekday calendar gate but uses the latest completed XTKS session; it is separate from scheduled weekday runs and is not a `run_mode` choice. The complete output is retained as a 30-day artifact.

Actions run #56 on 2026-10-17 processed 4,444 codes in 4,779.87 seconds and published a 4,341-item catalog for generation `2026-10-16`. The script reported 4,390 successful and 54 failed securities; the Actions job ran for 80m11s and ended with the expected partial-failure status. Collection took 4,646.337 seconds, catalog generation 121.904 seconds, and publication 5.582 seconds. It recorded 68 high-level yfinance calls, 82,568 `get_object`, 78,486 `get_body`, 14,850 `list_objects_v2`, and 70,468 `put_object` calls. A 23-session projection of the job duration is 1,844.2 runner-minutes, but same-session field reuse makes that projection unsuitable for confirming the ordinary monthly workload. The prior forced run #49 used 86,822 `get_object`, 74,967 `put_object`, and 151.735 seconds for catalog generation; run #56 used fewer of these operations, but the runs were not a controlled same-code comparison. Normal scheduled sessions are still required to confirm the 2,000-minute target and set the timeout.

The collector keeps a per-security cache of R2 objects for the duration of one worker task. Monthly-price migration lists existing year partitions before reading or deleting them, which avoids requests for absent keys. Scheduled collection uses 24 ticker workers; the Yahoo HTTP request-start limit remains 8 per second.

Catalog generation uses items returned by successful and partial ticker updates, then reuses the prior catalog row for symbols not refreshed or with a failed attempt. Failed symbols keep the last published quote and dividend values and receive a failure status. R2 profile/current/sync reads are used only when an item is missing from both the new results and the previous catalog, such as during initial migration. Securities that have never had a successful profile and close remain in the universe status list but stay out of search. Securities missing from the latest J-Quants list are marked inactive and are not fetched or newly searchable; their stored history remains in R2.

The Worker exposes v2 data through the app API; R2 public URLs remain disabled. Android stores its last successful catalog fetch time on each device and observes both the Japan-local daily limit and the 12-hour minimum interval. Search and registration use the published R2 catalog and do not trigger an on-demand yfinance request.

## GitHub configuration

The repository requires these Actions secrets:

- `JQUANTS_API_KEY`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`

The secrets must be added in the repository's Actions secrets settings before the scheduled collector can publish. Their values are never stored in the repository. Scheduled runs can be delayed during GitHub Actions load; the schedule is set away from the start of the hour to reduce this risk. GitHub automatically disables scheduled workflows in public repositories with no repository activity for 60 days, so periodically confirm the workflow remains active.

The R2 credentials should be scoped to read and write the `diview-market-data` bucket. `CLOUDFLARE_ACCOUNT_ID` and the bucket name are configured in the workflow. Manual dispatch defaults to a 40-security benchmark that does not access R2; select `sync` only when publishing a full scheduled-style generation is intended.

The first v2 run also migrates required values from existing `market/yfinance/securities/{symbol}.json` objects. It verifies the v2 profile, current data, event history, December price history, financial records, and legacy-field archive before deleting each migrated legacy object. On its rotating initial-price pass, a security's monthly history is reduced to the latest eight December closes; other month records and older year-end prices are pruned from the v2 price area. Migration is deferred for each security until its rotating history, finance, and year-end-price work have succeeded. The existing IRBANK namespace is not bulk archived or pruned.

## Retired collection paths

The prior `full`, `weekly-minimal`, and `publish-dividends` jobs have been removed from the production workflow so they cannot continue publishing into the legacy yfinance schema. Their scripts remain in the repository for historical reference and must not be used for scheduled production collection. The monthly rights-date workflow remains active and reads/writes only v2 objects.

## December close date repair

Existing December price points are normalized so `date` is the final XTKS session of the month, while `close` remains the saved yfinance monthly `Close`. Manual workflow mode `repair-monthly-prices` rewrites only affected date fields, reads every changed object back for verification, and makes no Yahoo/yfinance requests. It installs only `boto3` and `exchange_calendars` from `requirements-rights.txt`.

The production repair in Actions run #51 scanned 28,950 year partitions and normalized 25,680 points with zero failures and zero yfinance requests. Worker API read-back confirmed all eight 7203 December dates and all 142 available price points in a 20-security split/reverse-split sample matched the final XTKS session. One sample security (1491) had no stored price history.
