# yfinance v2 market data

The `yfinance-r2.yml` workflow is the scheduled collector. It starts at 21:17 Japan time on weekdays, checks the XTKS exchange calendar, obtains the current listed-security universe from J-Quants v2, and writes app-required yfinance data to `market/yfinance/v2/` in the private `diview-market-data` R2 bucket. It uses the standard GitHub-hosted Ubuntu runner; standard runners are free for public repositories.

The J-Quants master includes equities, ETFs, and REITs. Its product category is retained in the v2 universe, while the app continues to resolve industry names through its bundled industry master. Each J-Quants code is converted to a Yahoo Finance `.T` symbol. A security enters the search catalog only after its yfinance profile and completed daily close are available.

The collector pins `yfinance==1.7.0`, `scipy==1.18.1`, and `scikit-learn==1.9.1` so scheduled runs do not silently change price-repair or dividend-event behavior when a library release appears. yfinance's `repair=True` path uses SciPy for random unit-mixup detection and scikit-learn's DBSCAN when reconstructing damaged price intervals; without scikit-learn, some history requests fail before actions can be stored. Upgrade these dependencies deliberately and validate representative split, reverse-split, and ordinary dividend histories before publishing a new collector version. Rights-date calculation uses the separate `requirements-rights.txt` set (`exchange_calendars` and `boto3`) and does not install yfinance, SciPy, or scikit-learn.

## Published data

- `manifest.json`, `universe/current.json`, `catalog/current.json`, generation snapshots, and `publications/current.json` describe the active universe and publication state.
- `securities/{symbol}/profile.json` contains the Japanese-locale yfinance company profile and display-name fallback fields.
- `securities/{symbol}/current.json` contains the latest completed close and date, trailing 12-month dividends, Yahoo's `dividendRate` estimate for the next 12 months, current-fiscal-year dividend events observed through the collection date, yield, PER/PBR, and per-field retrieval state. `dividendRate` is not an issuer-confirmed next-fiscal-year DPS.
- `securities/{symbol}/prices/monthly/{year}.json` contains the latest eight completed December `Close` values (including the newest point); older points within the eight-year window remain under `archive/prices/monthly/{symbol}/{year}.json`.
- `securities/{symbol}/dividends/{year}.json` and `splits/{year}.json` contain the recent ten years of events. Older events move to `archive/events/{symbol}/{dividends|splits}/{year}.json` and are retained indefinitely. Recent events are checked daily with `period="1y"`; the complete repaired history is rechecked in one of 20 rotating groups, about once per month, and immediately when a newly detected split requires a complete refresh. A successful response replaces stored events inside its reported coverage so repaired amounts and removed duplicates replace older values. Event amounts are stored as returned after yfinance repair, with no second split-ratio adjustment in this pipeline. A failed fetch keeps previous events and records a retry state.
- The financial-data history chart sums yfinance-repaired distribution events by calendar year. It does not present IRBANK's adjusted fiscal-year DPS as an observed yfinance distribution or company-reported calendar-year total. Calendar-year sums can differ from issuer fiscal-year DPS, and the event share basis is not independently normalized. `current.json` records the action-history coverage, yfinance version, amount basis, and repair mode.
- App-required annual financial inputs are stored in `securities/{symbol}/financials/{fiscal-year}.json`; `sync.json` records attempts, last success, retry count, per-field state, and failure reason.
- Calculated XTKS rights-date data is published at `derived/rights_dates/current.json`. The calculation consumes only v2 event and current-data objects.
- Unused fields from a legacy yfinance security object are compressed under `archive/legacy/securities/{symbol}/unused.json.gz` and retained for ten years. The source object is removed only after the v2 data and archive have been read back and checked.

## Collection and publication behavior

The market calendar skips weekends and Japanese exchange holidays. Each trading day, all active securities refresh yfinance company/current statistics and one `history(period="1y", interval="1d", actions=True)` chart. The same response supplies the exact-session `Close` and latest-year dividend/split candidates, removing the former separate quote and actions requests. Only the current quote and event records are stored; the other daily rows are discarded. A missing same-session close fails that security's attempt, keeps the prior published close, and records a retry; a previous day's close is never relabeled as today's. Normal event comparisons read the latest three calendar-year partitions, enough for trailing-12-month and current-fiscal-year calculations. Unchanged daily candidates do not rewrite historical event partitions; migration, changed events, or full-history repairs update the affected event data. Full action history and the initial eight completed December closes are spread across 20 persistent rotating groups; this gives a roughly one-month first-pass/refresh cycle. A newly detected split or reverse split triggers a full action-history refresh and a fresh yfinance fetch of all eight December closes for that security, replacing the stored split-adjusted prices. Annual financial statements and valuation measures refresh when Yahoo's `lastFiscalYearEnd` or `mostRecentQuarter` marker changes, at the one-time five-group initialization pass, or after 45 days without a check. A retry fetches only financial groups previously marked failed. Same-session retries after a partial result reuse successful profile, close, action, and financial groups; required daily market fields still refresh on the next market session. December closes are refreshed for all securities after the last Tokyo trading session in December. Each ticker is attempted at most four times per market day across repeated workflow executions. Empty dividend/split histories remain distinct from failures.

The publication record and Actions log include elapsed synchronization seconds, per-phase timings, R2 request counts and timings, and counts of high-level yfinance requests by method. The monthly scheduled-run target is at most 2,000 GitHub-hosted runner minutes; complete runs are required to confirm it. The workflow runs deterministic Python sync tests on relevant pushes and pull requests and supports manual `test`, `benchmark`, and `sync` modes. The benchmark uses a J-Quants sample and makes no R2 writes. It measures the production-shaped daily chart request and compares unrepaired daily-chart action candidates with repaired history on up to six sample securities, reporting elapsed time, HTTP response count, decoded response-body bytes, event counts, and event fingerprints. Repaired history remains authoritative when a candidate indicates a change.

Manual `benchmark` runs accept 16 or 24 ticker workers while keeping the HTTP request-start limit at 8 per second. A push whose commit message contains `[yfinance-capacity-study]` runs a sequential, non-publishing comparison of 20 securities at 16 workers, 500 securities at 16 workers, and 500 securities at 24 workers; the three reports are saved as a 30-day workflow artifact. The benchmark probes 7203.T and uses the earlier of its latest available close and the latest completed XTKS session, reporting both dates, profile success, exact-close availability, and total benchmark time. Production sync still requires the exact latest completed XTKS close. The benchmark fails on any HTTP 429, profile failure above 10%, or exact-close availability below 50%; individual securities without a close are listed in the report. This marker is intended for a deliberate capacity measurement because it consumes Actions time and makes Yahoo requests.

A push whose commit message contains `[yfinance-full-universe-study]` runs and publishes the full J-Quants universe to R2 with 24 workers and the same 8-requests-per-second limit. It reprocesses securities already successful for the current market session so repeated runs measure the actual synchronization workload. This manual measurement bypasses the weekday calendar gate but the collector still uses its latest completed XTKS session; it is separate from the scheduled weekday run. The complete output is retained as a 30-day artifact.

The collector keeps a per-security cache of R2 objects for the duration of one worker task. Monthly-price migration lists existing year partitions before reading or deleting them, which avoids requests for absent keys. Scheduled collection uses 24 ticker workers; the Yahoo HTTP request-start limit remains 8 per second.

Catalog generation uses items returned by successful and partial ticker updates, then reuses the prior catalog row for symbols not refreshed or with a failed attempt. Failed symbols keep the last published quote and dividend values and receive a failure status. R2 profile/current/sync reads are used only when an item is missing from both the new results and the previous catalog, such as during initial migration. Securities that have never had a successful profile and close remain in the universe status list but stay out of search. Securities missing from the latest J-Quants list are marked inactive and are not fetched or newly searchable; their stored history remains in R2.

The Worker exposes v2 data through the app API; R2 public URLs remain disabled. Android stores its last successful catalog fetch time on each device and observes both the Japan-local daily limit and the 12-hour minimum interval. Search and registration use the published R2 catalog and do not trigger an on-demand yfinance request.

## GitHub configuration

The repository requires these Actions secrets:

- `JQUANTS_API_KEY`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`

The secrets must be added in the repository's Actions secrets settings before the scheduled collector can publish. Their values are never stored in the repository. Scheduled runs can be delayed during GitHub Actions load; the schedule is set away from the start of the hour to reduce this risk. GitHub automatically disables scheduled workflows in public repositories with no repository activity for 60 days, so periodically confirm the workflow remains active.

The R2 credentials should be scoped to read and write the `diview-market-data` bucket. `CLOUDFLARE_ACCOUNT_ID` and the bucket name are configured in the workflow. Manual dispatch defaults to a 40-security benchmark that does not access R2; select `sync` only when publishing a full scheduled-style generation is intended.

The first v2 run also migrates required values from existing `market/yfinance/securities/{symbol}.json` objects. It verifies the v2 profile, current data, event history, December price history, financial records, and legacy-field archive before deleting each migrated legacy object. On its rotating initial-price pass, a security's monthly history is reduced to the latest eight December closes; other month records and older year-end prices are pruned from the v2 price area. Migration is deferred for each security until its rotating history, finance, and year-end-price work have succeeded. The existing IRBANK namespace is not bulk archived or pruned.

## Retired collection paths

The prior `full`, `weekly-minimal`, and `publish-dividends` jobs have been removed from the production workflow so they cannot continue publishing into the legacy yfinance schema. Their scripts remain in the repository for historical reference and must not be used for scheduled production collection. The monthly rights-date workflow remains active and reads/writes only v2 objects.
