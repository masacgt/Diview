# yfinance v2 market data

The `yfinance-r2.yml` workflow is the scheduled collector. Its weekday cron is configured for 21:17 JST; GitHub may start a scheduled run later. The workflow checks the XTKS exchange calendar, reads the complete weekly IRBANK Connect `/v1/securities` snapshot from R2, and writes app-required yfinance data to `market/yfinance/v2/` in the private `diview-market-data` R2 bucket. It does not request a J-Quants or IRBANK code list during daily sync. It uses the standard GitHub-hosted Ubuntu runner; standard runners are free for public repositories.

The separate IRBANK batch workflow refreshes the full cursor-paginated security list when its R2 snapshot is at least seven days old. It shares a maximum of 200 IRBANK API requests per run with the dividend batch; incomplete refreshes preserve the last valid snapshot. The remaining API budget can still be used by that run's dividend batch, and the workflow ends in failure if the universe refresh is overdue or failed. The yfinance daily sync fails closed if no valid schema-v2 snapshot exists. Five-character ordinary codes ending in `0` are normalized to their four-character display form (including alphanumeric codes such as `130A0`); other five-character class codes such as `92025` are preserved, then `.T` is appended for Yahoo Finance. The weekly snapshot uses IRBANK as its base and supplements it with all currently listed ETFs from JPX's public issue table. It filters future listing dates using the JST refresh date, tags ETF rows with `security_type=etf` and `jquants_product_category=014`, and retains both provider provenance and the official listing date. Missing/malformed tables, duplicate codes, invalid dates, or fewer than 350 currently listed ETF rows fail the refresh before R2 publication. Existing product-category metadata is carried forward for matching codes; other new codes default to `listed_security` until classified. Industry names still come from the app's bundled industry master. A security enters the search catalog only after its yfinance profile and completed daily close are available. A read-only one-batch yfinance 1.7.0 probe of seven J-Quants-only class-share symbols returned some five-day history for all seven, but only 75505.T and 92025.T had a 2026-11-02 close; this single request does not establish reliable daily coverage or catalog eligibility, and it did not write R2. See `ai_docs/audits/irbank-jquants-universe-diff-20261103.json`.

The read-only `audit_universe_sources.py` compares IRBANK and J-Quants snapshots, reporting raw and normalized codes, duplicates, each membership difference, and J-Quants product categories. It keeps API retrieval time separate from the source's effective date and flags non-aligned effective dates. The 2026-11-03 comparison fetched IRBANK at `2026-11-02T17:32:30Z` and J-Quants at `2026-11-02T17:32:46Z`; retrievals were 16 seconds apart, but J-Quants' master data was still dated `2026-08-10`. IRBANK had 4,573 unique codes and J-Quants 4,444; 4,406 overlapped, with 167 IRBANK-only and 38 J-Quants-only, and zero duplicates. J-Quants categories were 011: 3,897, 012: 2, 013: 63, 014: 421, 021: 5, 023: 56. Among the differences, IRBANK identifies one ETF (1553); J-Quants identifies 37 equities and one ETF (2643). A read-only check against JPX's public delisted-stocks table matched 30 differences: 28 J-Quants-only codes were delisted after the J-Quants 2026-08-10 effective date and by the IRBANK retrieval date, while two IRBANK-only codes (6565 and 5386) had already been delisted before both snapshots but remained in the IRBANK response. The remaining 175 differences are unclassified; the 28 matches are consistent with source-date drift, while the two IRBANK entries demonstrate retained delisted codes without establishing why. The audit report contains all membership-difference rows, the cross-check evidence, normalization hashes and representative raw-to-display examples (including `13010 → 1301` and `130A0 → 130A`) in [`ai_docs/audits/irbank-jquants-universe-diff-20261103.json`](../../ai_docs/audits/irbank-jquants-universe-diff-20261103.json); there were 4,437 normalized codes in total. The source snapshots remain local. A same-day comparison with JPX's official ETF list found 417 currently listed ETFs and three absent from IRBANK (650A, 651A, 659A); all 58 JPX-listed REITs were in IRBANK. J-Quants documents a 12-week delay on the free plan and its master does not provide listing/delisting dates.

A second read-only cross-check used JPX's official September 2026 month-end TSE-listed issues workbook (snapshot 2026-09-30; SHA-256 `a26fdf4420cb6a152a1811ce0c6e293e642c8a99f1cc2ad9c47a5d55f2722c82`). It contains 42 of the 205 membership-difference codes: 25 IRBANK-only and 17 J-Quants-only. Seven J-Quants-only codes (25935, 50765, 75505, 92015, 92025, 94345, 94346) are identified by the JPX issue names as class shares. The dated list establishes TSE presence on 2026-09-30 only; it does not establish why the other source omitted a code, exact listing dates, or status on 2026-11-02, and absence does not rule out another exchange. See the `jpx_tse_snapshot_check` records in the audit JSON. This class-share cohort is a product-scope question before any universe supplementation.

Manual workflow mode `refresh-company-info` forces `Ticker.get_info()` for every active security, including securities already processed during that market session. It runs the regular V2 sync with 24 workers and an eight-request-per-second limit, then publishes the updated security data and catalog to R2. It allows one extra per-security attempt beyond the normal daily cap.

The collector pins `yfinance==1.7.0`, `scipy==1.18.1`, and `scikit-learn==1.9.1` so scheduled runs do not silently change price-repair or dividend-event behavior when a library release appears. yfinance's `repair=True` path uses SciPy for random unit-mixup detection and scikit-learn's DBSCAN when reconstructing damaged price intervals; without scikit-learn, some history requests fail before actions can be stored. Upgrade these dependencies deliberately and validate representative split, reverse-split, and ordinary dividend histories before publishing a new collector version. Rights-date calculation uses the separate `requirements-rights.txt` set (`exchange_calendars` and `boto3`) and does not install yfinance, SciPy, or scikit-learn.

Manual workflow mode `split-audit` performs a read-only comparison for current securities with split or reverse-split events in the latest eight years. It reads dated yfinance event partitions from R2 and compares their fiscal-period sums with the processed issuer `annual_dps_adjusted` snapshot, using each reported fiscal-period end date to assign events. It writes per-security and per-fiscal-year CSV files plus a summary artifact; it never writes to R2 or changes the app's yfinance-only data path. Missing issuer DPS, missing fiscal dates, failed yfinance history, and numerical mismatches remain separate outcomes. A mismatch identifies a case for source-level review; it does not by itself establish which source is wrong. The latest full-universe audit, [Actions run #176](https://github.com/masacgt/Diview/actions/runs/39383687304), selected 1,068 securities and 1,270 split events from 4,435 active codes and completed with zero technical failures. The artifact includes 7,345 fiscal-year rows; 7,336 were marked `compared`, with 6,206 within ¥0.05 per share and 1,130 outside tolerance. Nine 8303 rows are marked `yfinance_failed` and should not be counted as numeric comparisons, although the artifact summary's headline totals include them. The audit is a candidate report, not proof that either source is wrong.

## Published data

- `manifest.json`, `universe/current.json`, `catalog/current.json`, generation snapshots, and `publications/current.json` describe the active universe and publication state.
- `securities/{symbol}/profile.json` contains security identifiers and the Japanese-locale display-name fallback fields. Exchange, country, business summary, market capitalization, and profile-level shares outstanding are not retained; the weekly IRBANK snapshot supplies the active code universe. Existing product-category metadata is retained where available for prior codes; new IRBANK codes default to `listed_security` until classified. Currency is stored with the current quote.
- `securities/{symbol}/current.json` contains the latest completed close and date, same-chart previous close and daily change, trailing 12-month dividends, Yahoo's `dividendRate` estimate for the next 12 months, current-fiscal-year dividend events observed through the collection date, yield, and per-field retrieval state. Yahoo's reported `trailingPE` and `priceToBook` are preferred; the latest close divided by positive `trailingEps` or `bookValue` is used when the corresponding Yahoo statistic is unavailable. The recorded calculation metadata identifies each value's source and price/statistics dates. The R2 current yield prefers Yahoo's reported `dividendYield` and falls back to the yfinance dividend and quote calculation. Worker endpoints prefer Yahoo's reported value, then IRBANK screening yield, then the annual-dividend and quote calculation. Historical yield minimum, average, and maximum retain their existing calculation. `dividendRate` is not an issuer-confirmed next-fiscal-year DPS. The reported `operatingMargins` statistic is retained for analysis and converted to percent; annual operating profit divided by sales remains the fallback.
- `sync.json` records the company-information refresh status, successful and attempted dates, retry state, and structured failure class/reason. Fields removed from the current statistics object are copied once into `archive/unused_statistics/{symbol}/statistics.json`. The collector stores an upcoming ex-dividend date from `Ticker.calendar` when that field is due for refresh; the Worker falls back to `statistics.exDividendDate` from `Ticker.get_info` when no calendar date is stored. The API labels the selected source and status. The Android Stock Detail screen requests `/api/v1/dividend-months` for the viewed security once per JST date; empty upcoming-event data displays as unavailable, while request failures preserve cached values and remain eligible for retry.
- `securities/{symbol}/prices/monthly/{year}.json` contains the latest eight completed December `Close` values (including the newest point); older points within the eight-year window remain under `archive/prices/monthly/{symbol}/{year}.json`.
- Each December price point's `date` is the final XTKS session of that December; the yfinance monthly candle timestamp is not used as the close date. Manual workflow mode `repair-monthly-prices` normalizes dates in existing R2 partitions, verifies each rewritten object, and makes no Yahoo/yfinance requests. The scheduled writer applies the same normalization when it next touches a security.
- `securities/{symbol}/dividends/{year}.json` and `splits/{year}.json` contain the recent ten years of events. Older events move to `archive/events/{symbol}/{dividends|splits}/{year}.json` and are retained indefinitely. The daily one-year price chart also supplies unrepaired dividend/split candidates for change detection; these candidates never replace stored repaired events. When an event is new or changed, the collector fetches the affected coverage again with `history(actions=True, repair=True)` and replaces the successful range. Complete repaired history is rechecked in one of 20 rotating groups, about once per month, and immediately when a newly detected split requires a complete refresh. Event amounts are stored as returned after yfinance repair, with no second split-ratio adjustment in this pipeline. A failed fetch keeps previous events and records a retry state.
- The financial-data history chart sums yfinance-repaired distribution events by calendar year. It does not present IRBANK's adjusted fiscal-year DPS as an observed yfinance distribution or company-reported calendar-year total. Calendar-year sums can differ from issuer fiscal-year DPS, and the event share basis is not independently normalized. `current.json` records the action-history coverage, yfinance version, amount basis, and repair mode.
- App-required annual financial inputs are stored in `securities/{symbol}/financials/{period-end}.json`, using the full `YYYY-MM-DD` reporting date so distinct fiscal periods that end in the same calendar year remain separate. Existing `YYYY.json` partitions are still read and updated when they already contain the exact period. The records contain sales and operating income, stockholders' equity and total assets, operating and investing cash flow, plus yearly EPS, book value, and dividend yield. The yfinance cash-flow rows `CommonStockDividendPaid` and `CashDividendsPaid` are also retained. When a matching annual record contains a positive `StockholdersEquity` and a cash-dividend-paid value, `calculated_doe` is computed as the absolute dividend cash outflow divided by fiscal-period-end stockholders' equity, times 100. Common-stock dividends are preferred; total cash dividends are used only if that row is absent. The source field, formula, and per-field state are stored with the annual record. The calculation uses yfinance reported cash flow for the fiscal period and is distinct from an issuer-published DOE. For net D/E, the collector prefers yfinance `NetDebt`; if absent, it calculates total debt less cash and short-term investments (or cash and cash equivalents) for that same period. It divides net debt by positive `StockholdersEquity`, falling back to total equity including minority interests; incomplete inputs or non-positive equity leave the ratio unavailable. The source fields, formula, and field state are stored with the annual record. Policy version 2 schedules existing securities through the rotating five-group initialization so the new value is collected before the normal fiscal-marker or 45-day refresh. Unused statement rows such as net income, statement EPS, shares outstanding, and capital expenditure are not retained. `sync.json` records attempts, last success, retry count, per-field state, and failure reason.
- A security absent from per-security V2 sync state gets annual financial initialization on its first normal universe sync. The `refresh-all-financials` Actions mode explicitly refreshes all annual financial groups for every active security in the published V2 universe using eight disjoint shards, writes each period to R2, and verifies values, metric states, and missing-input reasons by reading them back. Each shard saves its own report artifact. Each annual row carries `field_status_reason` for calculated DOE and net D/E, including statement-fetch failures and missing same-period inputs. These reasons pass through the financial-data API with the annual record. This operation is server-side; the Android app continues to request the published API record when adding a security.

IRBANK source metadata is preserved under `source_values.seed.field_units`; the shared field contract fills in only missing unit metadata during migration. The Worker normalizes every declared `million_jpy` or `hundred_million_jpy` seed amount to JPY in flat API rows and retains the original amount and unit in `financials.seed_annual`. Unknown or unsupported units stay unconverted and Android omits fields whose API unit is not the expected one. This lets seed-only margins use compatible values without a million-fold mismatch. Equity-ratio calculations require matching input sources and explicit compatible units; otherwise the Worker uses a unit-verified IRBANK reported percentage or omits the ratio. Ratios above 1,000% remain rejected. yfinance monetary values are JPY. Migration read-back checks include seed units and calculation provenance.

Earlier remediation for the 7203 and 4502 equity-ratio cases retained their same-period IRBANK ratios (37.829768942% and 47.896322897%). The prior full-universe migration processed 4,442 securities and verified every changed object; the new unit metadata and historical outlier repair require a fresh migration after publication.

### One-time migration of existing financial values

The preferred-share symbols `92025`, `25935`, `92015`, `94346`, `50765`, `75505`, and `94345` are reported as `preferred_security_excluded`: IRBANK has no separate four-character issuer record for these issues, so the migration does not substitute the issuer's ordinary-share data. Other unsupported symbol formats remain separately reported as `unsupported_code`.

The manual Actions mode `migrate-financials` copies app-used annual fields that are still missing from existing `market/irbank/v1/securities/{code}/overview.json` objects into `market/yfinance/v2/securities/{symbol}/financials/{period-end}.json`. Full period-end keys allow legacy and yfinance records with different fiscal year ends in the same calendar year to coexist. It marks copied fields as `legacy_migrated`, retains their values and IRBANK source reference under `annual.source_values.seed` or `valuation.source_values.seed`, records source field units, and reads every changed object back before reporting success. The full-universe migration runs as four deterministic, disjoint code shards. Each shard writes an atomic progress report every 100 securities and at exit, and Actions retains one report artifact per shard for 30 days. Reruns preserve migrated seed values while removing obsolete cross-source, unknown-source, and implausible equity-ratio calculations; a same-period seed ratio is kept when valid, otherwise the field is marked empty. Read-back checks cover field status, unit metadata, and calculated source records. It does not fetch Yahoo data or delete the source objects. It is safe to rerun to fill remaining missing seed values without overwriting existing ones. The collector records later Yahoo values separately under `source_values.yfinance`; the flat values used by the existing app contract prefer yfinance when present, while the seed remains available. Derived metrics identify calculation inputs and their source category. The Worker also exposes retained seed records separately as `financials.seed_annual` and `valuation.seed_history`, and keeps the existing annual/history fields for app compatibility. Older flat v2 records are classified from their field status and migration marker when the source-specific object is first updated. Run #175 (`39378087521`) processed 4,442 securities: 125 were newly migrated (1,219 fields), 3,566 were already seeded, 517 had no legacy values to migrate, 227 had no app-used fields, and 7 codes were unsupported; all changed R2 objects passed read-back verification.

The manual Actions mode `migrate-irbank-dividends` copies legacy issuer-reported fiscal-year dividend rows into `market/yfinance/v2/securities/{symbol}/issuer_dividends/{fiscal-year}.json`. It reads `market/irbank/v1/securities/{code}/dividends.json` first and falls back to `market/securities/v1/{code}.json`; each row keeps its fiscal-year values, source references, and attribution. Existing v2 fiscal-year rows are preserved, every inserted row is read back, and source objects and dated yfinance event partitions are not changed. The Worker financial-data response returns these issuer records separately from its calendar-year yfinance event totals. This migration does not infer event dates or convert fiscal-year DPS into calendar-year distributions; issuer records are retained as seed data while future yfinance event records are added separately.
- Calculated XTKS rights-date data is published at `derived/rights_dates/current.json`. The calculation consumes only v2 event and current-data objects. It reads event partitions from the current calendar year back through `as_of_year - ESTIMATE_LOOKBACK_YEARS` (six calendar years with the current value of five), which covers the inclusive recurrence-estimation boundary and the current/previous-year output window. Older retained event partitions remain in R2 and are not deleted; they are outside this job's calculation window. This reduces eligible historical-partition GETs from ten years to six per security. The workflow currently does not report R2 operation counters; add those before the next scheduled measurement. End-to-end runner-time savings remain unmeasured.
- The first `derived/income_advice/current.json` publication is a separate R2-only reaggregation. Run the manual `generate-income-advice` workflow mode to read the published V2 catalog, current/statistics documents, latest annual financial rows, and the last three completed calendar years of dividend events; it computes eligible candidates, writes the derived object, and verifies the R2 read-back. It makes no Yahoo or J-Quants requests. Normal V2 catalog syncs refresh this derived object as part of their publication.
- Unused fields from a legacy yfinance security object are compressed under `archive/legacy/securities/{symbol}/unused.json.gz` and retained for ten years. The source object is removed only after the v2 data and archive have been read back and checked.

## Collection and publication behavior

Current universe source (production implementation; normal-schedule verification pending): the separate IRBANK batch workflow checks the R2 snapshot age daily at 02:17 JST and refreshes it from all `/v1/securities` cursor pages when it is at least seven days old. The complete snapshot is validated and read back before it is used. The workflow shares a maximum of 200 IRBANK API requests with the daily dividend batch. The yfinance job at 21:17 JST reads only the saved R2 list. It does not call J-Quants or IRBANK, and it fails closed if the saved list is missing or invalid. J-Quants remains in sample/benchmark jobs and historical run records from before the source switch. PR #45 is merged as `ced28fc5`; IRBANK run #13 refreshed 4,573 IRBANK codes plus three JPX ETFs (4,576 total) and verified the R2 read-back hash. The first manual full sync #314 processed that snapshot and published a 4,358-item catalog. This proves manual production publication, not normal scheduled calendar-gate behavior. New IRBANK codes without retained product-category metadata default to `listed_security`; only the missing ETF additions are explicitly supplemented from JPX.

The market calendar skips weekends and Japanese exchange holidays. If GitHub delays a scheduled run past midnight, the calendar gate compares the latest completed XTKS session with R2's published session and recovers that session only when it is still unpublished; it passes the selected session date into the collector. On a closed day whose latest completed session is already published, the gate skips reading the IRBANK universe snapshot and skips yfinance. R2 state read errors fail the gate rather than causing an unverified catch-up. Each trading day, all active securities refresh the exact-session `Close` and latest-year dividend/split candidates from one `history(period="1y", interval="1d", actions=True)` chart. Company names and `Ticker.get_info()` statistics use a stable five-bucket rotation: each security is refreshed once per five published XTKS sessions, using the same active bucket as the financial rotation. New securities fetch company information before entering the catalog, and a failed refresh keeps the previous values and is retried on the next session. R2 `sync.json` and `current.json` record the latest successful information-fetch session; cached statistics are marked stale between refreshes. Daily yield calculations continue to use the current price and event history plus the most recently fetched `get_info()` dividend inputs. Normally these inputs are at most four XTKS sessions old; after a failed refresh or missed sync they remain marked stale until a fetch succeeds. The daily chart's other price and volume rows are discarded. A missing same-session close fails that security's attempt, keeps the prior published close, and records a retry; a previous day's close is never relabeled as today's. Normal event comparisons read the latest three calendar-year partitions, enough for trailing-12-month and current-fiscal-year calculations. Unchanged daily candidates do not rewrite historical event partitions; migration, changed events, or full-history repairs update the affected event data. Full action history and the initial eight completed December closes are spread across 20 persistent rotating groups; this gives a roughly one-month first-pass/refresh cycle. A newly detected split or reverse split triggers a full action-history refresh and a fresh yfinance fetch of all eight December closes for that security, replacing the stored split-adjusted prices. Annual financial statements and valuation measures refresh when Yahoo's `lastFiscalYearEnd` or `mostRecentQuarter` marker changes, at the one-time five-group initialization pass, or after 45 days without a check. A retry fetches only financial groups previously marked failed. Same-session retries after a partial result reuse successful company-information, close, action, and financial results; required daily market fields still refresh on the next market session. December closes are refreshed for all securities after the last Tokyo trading session in December. Each ticker is attempted at most four times per market day across repeated workflow executions. Empty dividend/split histories remain distinct from failures. Yahoo `YFPricesMissingError` and HTTP 404 are stored as `no_data` and are not retried again during the same market session; they are reconsidered on the next session. HTTP 408/425/429/5xx and timeout/connection errors are classified as transient and remain retryable within the four-attempt daily cap. Other exceptions are marked `unknown` for diagnosis.

Manual `refresh-company-info` mode runs the full-universe sync with `--refresh-company-info`, forcing `Ticker.get_info()` for every active security instead of waiting for its five-session bucket. It updates the current profile/statistics and republishes the catalog to R2 using the normal collector path. The mode uses the latest completed XTKS session, may be run on a closed market day, and shares the normal 360-minute job limit and yfinance request-rate limit. Use it after deploying a new current-statistics field to backfill the active universe.

The publication record and Actions log include elapsed synchronization seconds, per-phase timings, R2 request counts and timings, and counts of high-level yfinance requests by method. During per-security collection, the publication also records the union of yfinance-request and R2-request active wall time, their overlap, and the yfinance-only, R2-only, and idle portions. These intervals distinguish time spent waiting on each service from worker count alone; they do not include Actions setup, dependency installation, the separate weekly IRBANK refresh, or catalog publication. The monthly target for the yfinance daily workflow is at most 2,000 GitHub-hosted runner minutes and remains unverified. Its per-phase metrics exclude the separate IRBANK batch workflow; any combined Actions-minute budget must also count that workflow, including the dividend batch and its weekly universe refresh. The workflow runs deterministic Python sync tests on relevant pushes and pull requests. Manual `check-calendar` mode runs only the XTKS/R2 publication-state gate and never starts a universe refresh, yfinance, or R2 writes; use it to verify credentials and the selected session before relying on scheduled recovery. Manual `refresh-financials` refreshes one ticker's annual financial records and verifies their V2 read-back without rebuilding the full-universe catalog. Other modes include `test`, `benchmark`, `sync`, `migrate-financials`, `reaggregate-dividend-streaks`, `repair-monthly-prices`, and `split-audit`. The benchmark uses a J-Quants sample and makes no R2 writes. It compares unrepaired daily-chart action candidates with repaired history for every sampled security and reports response counts, decoded response-body bytes, event counts, and fingerprints. A separate per-symbol JSON artifact retains event rows and comparison errors. For a 500-security sample, the selector prioritizes all recent split/reverse-split codes present in the J-Quants universe. The existing split-event catalog is used only to choose a representative sample; it is not used as event data or as the comparison's expected values. Repaired history remains authoritative when a candidate indicates a change.

Manual `benchmark` runs accept 16 or 24 ticker workers while keeping the HTTP request-start limit at 8 per second. A push whose commit message contains `[yfinance-capacity-study]` runs a sequential, non-publishing comparison of 20 securities at 16 workers, 500 securities at 16 workers, and 500 securities at 24 workers; summary logs and per-symbol JSON reports are saved as a 30-day workflow artifact.
