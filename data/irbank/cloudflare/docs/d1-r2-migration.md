# D1 to R2 migration runbook

## Read the current UTC-day D1 usage without issuing D1 SQL

The dashboard and Wrangler `rows_read_24h` observations did not agree during the 2026-11-04 audit. To inspect the current UTC day's account-wide rows-read count before any further D1 row query, use the read-only GraphQL Analytics helper. It queries `d1AnalyticsAdaptiveGroups` for the account and UTC date, groups by database ID, and sums `rowsRead`; it never calls the D1 SQL API. Cloudflare's [D1 Dashboard charts](https://developers.cloudflare.com/d1/observability/metrics-analytics/) use this GraphQL analytics dataset, and the API token must have [Account Analytics Read permission](https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/).

Set `CLOUDFLARE_API_TOKEN` in the current shell using an existing token with Account Analytics Read permission, then run from this directory:

```powershell
$env:CLOUDFLARE_API_TOKEN = '<existing Account Analytics Read token>'
python scripts/d1_daily_usage.py --account-id '<Cloudflare account ID>'
```

The default daily limit is 5,000,000 rows for Workers Free; pass `--daily-limit` if the account plan or allowance differs. The output includes the UTC date, returned database IDs, each database's read count, account total, and remaining allowance. The token is read only from the environment and is never printed. A missing token or malformed API response stops before returning a usage total. If the GraphQL result disagrees with Dashboard billable usage or otherwise appears incomplete, leave the remaining allowance unresolved and do not run D1 row SQL. This helper does not establish that the deployed Worker has been cut over.

## Read live Queue backlog before retaining or archiving legacy rows

`wrangler queues info` confirms Queue configuration but does not report the live backlog. Cloudflare exposes best-effort point-in-time backlog metrics at `GET /accounts/{account_id}/queues/{queue_id}/metrics`; the response includes `backlog_count`, `backlog_bytes`, and `oldest_message_timestamp_ms`. The REST endpoint accepts Queues Read or Workers Scripts Read permission ([Cloudflare API](https://developers.cloudflare.com/api/resources/queues/methods/get_metrics/)). Use a dedicated `CLOUDFLARE_QUEUE_READ_TOKEN` for that scope; the Account Analytics-only `CLOUDFLARE_API_TOKEN` returned HTTP 403 in the current audit. Do not purge or acknowledge messages during this audit. The currently registered IDs are `diview-market-prices` = `41eb5b575a1e40d8aa9c99e6f6f8da22` and `diview-market-prices-dlq` = `7415d709130a495f9ad8e039fa6885d8`.

```powershell
$queueIds = @{
    'diview-market-prices' = '41eb5b575a1e40d8aa9c99e6f6f8da22'
    'diview-market-prices-dlq' = '7415d709130a495f9ad8e039fa6885d8'
}
$queueToken = $env:CLOUDFLARE_QUEUE_READ_TOKEN
if ([string]::IsNullOrWhiteSpace($queueToken)) { throw 'Set CLOUDFLARE_QUEUE_READ_TOKEN with Queues Read or Workers Scripts Read permission.' }
$headers = @{ Authorization = "Bearer $queueToken" }
foreach ($entry in $queueIds.GetEnumerator()) {
    $uri = "https://api.cloudflare.com/client/v4/accounts/$env:CLOUDFLARE_ACCOUNT_ID/queues/$($entry.Value)/metrics"
    $response = Invoke-RestMethod -Method Get -Uri $uri -Headers $headers
    [pscustomobject]@{
        queue = $entry.Key
        backlog_count = $response.result.backlog_count
        backlog_bytes = $response.result.backlog_bytes
        oldest_message_timestamp_ms = $response.result.oldest_message_timestamp_ms
    }
}
```

The Account Analytics GraphQL backlog dataset returned no samples for either queue during the 2026-11-03 14:00–2026-11-04 14:01 UTC audit window. This is historical analytics and does not prove a zero live backlog. The point-in-time REST request using the Account Analytics token returned HTTP 403 for both queues; a token with one of the documented REST permissions is still required.

Treat these metrics as an approximate snapshot, not proof of historical completion or absence of external producers. Also verify the current Worker Version, registered producers, backup/retention requirements, and dead-letter handling before removing bindings or D1 rows. Cloudflare documents this endpoint in [Get Queue Metrics](https://developers.cloudflare.com/api/resources/queues/methods/get_metrics/).

This runbook describes the local migration implementation and the manual GitHub Actions workflow. No production migration, GitHub Actions run, or Worker deployment is performed by the implementation change itself.

## Migration guarantees and limits

- The only D1 operation allowed by the reader is one `SELECT` statement. Each Cloudflare response must include `meta.rows_read`; the job stops if it cannot enforce the configured budget. During the bounded DO handoff window, a new bucket may look up its legacy D1 counter once. When D1 is bound, `RATE_LIMITER_D1_FENCE_AT` and `RATE_LIMITER_D1_IMPORT_UNTIL` are validated on every valid counter request before the DO reads its saved counter or seed marker. Missing or malformed values, a future fence, or a cutoff shorter than one configured window after the fence fail closed, including for already initialized actors. At/after the cutoff, a new bucket does not query D1. The SQLite seed marker persists after counter cleanup, and a delayed alarm does not extend an expired window.
- `d1-schema-audit` and `d1-operational-audit` are dry-run-only phases. They use only the D1 read credential; their workflow steps do not receive R2 S3 keys or install the R2 client. Other phases separately require the R2 credentials. The schema query inventories all table and trigger names, including SQLite system names. The operational phase uses rowid keyset pages and reports only aggregates plus sanitized backend-state keys; it never selects `backend_state.value_json`, scheduled-run IDs or metadata, or refresh run IDs. Checkpoint artifacts let an operator continue within the approved per-dispatch `rows_read` budget.
- `max_rows` limits D1 `rows_read` for one workflow dispatch. `batch_size` controls keyset pages. The three `market-source-audit` queries use a `LEFT JOIN`; they reserve up to two D1 row reads per returned row when choosing each page size, then account for Cloudflare's actual `meta.rows_read`. If an actual response exceeds the remaining budget, the report records the returned count and `budget_exceeded: true` before stopping. Use a small budget first, inspect the report, then resume from a checkpoint artifact by entering the earlier workflow run ID.
- A D1 API query is a POST, so the migration client never retries a failed or timed-out request automatically. The request may have executed even when its response was lost. The failure report records the attempted query count and sets `d1_read_count_unknown: true` when Cloudflare did not return enforceable `rows_read` metadata. `d1_rows_returned_without_meta` records a known lower bound if rows were returned; check current D1 usage before resuming.
- Checkpoints contain phase, table, the numeric keyset cursor needed for resumption, cumulative counts, rolling source hash, time ranges, R2 readback hash, pinned market-catalog generation and content hash, issuer-index hash when available, IRBANK manifest hash, market-audit field counts, source-audit status and field counts, period range, and R2 object hashes indexed by SHA-256 key fingerprints. The scheduled-run checkpoint keeps only run ID, type, and start time until the final pointer is published; it does not store the R2 key. Reports contain aggregate counts, hashes, time ranges, timestamps, and field names. They do not include source row bodies, compared values, per-row codes/names/periods, raw R2 keys, or samples. Legacy checkpoints have earlier samples removed, raw source keys fingerprinted, and analysis-current code cursors restarted from the beginning when resumed. Neither artifact contains credentials. On resume, the audit stops if a pinned R2 object changed, so a report cannot silently combine source generations.
- Dry-run is the default. It reads R2 for existence and conflict checks but performs no R2 writes. `market-audit` and `market-source-audit` are permanently read-only.
- Immutable keys use R2 conditional create-once writes. A key with different content is a conflict. Mutable current analysis/source objects use ETag-conditional updates and compare timestamps before replacing data. After every write, the script reads the object back and checks its bytes; a mismatch fails the run. Existing matching objects are also read and included in the verification digest.
- The R2 S3 API documents conditional `PutObject` writes (`If-Match` and `If-None-Match`), and R2 documents strong consistency for object writes and reads. The migrator uses those conditions for create-once and compare-and-set behavior; see [R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/) and [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).
- Worker analysis history and definition-audit objects use conditional create-once writes. Current per-security snapshots use ETag compare-and-set and refuse to replace a newer observation; the scheduled-run pointer advances monotonically, run summaries are updated against their last ETag, and the source-generation pointer is advanced only if its inputs remain unchanged. Conditional write conflicts are covered by local Worker tests.
- Analysis history retention compares each object's stored `observed_at`, not its R2 upload time. A daily ETag-claimed retention pass keeps every observation younger than 30 days, the newest observation for each UTC day from 30 to 365 days, and the newest observation for each UTC month older than 365 days. The same pass removes completed run summaries older than 365 days; it leaves the current-run pointer intact. The retention state lease expires after six hours so an interrupted pass can retry. This pass reads old history objects from R2 and its Class A/B operation volume must be measured after cutover.
- The market audit pins R2 catalog, issuer-index, and IRBANK-manifest content across checkpoint resumes; each compared IRBANK overview must also match its manifest SHA-256. It uses D1 `rowid` pagination so empty or duplicate display codes cannot be skipped at page boundaries. Invalid display codes are reported separately from valid codes missing in R2. If a pinned object changes, restart the audit so the report does not combine two snapshots.
- An incomplete report or checkpoint has `complete: false`. Re-run with the latest checkpoint artifact. A completed checkpoint can be resumed safely; newly appended keyset rows are still discoverable after its cursor.
- Checkpoints record their `dry_run` mode. A checkpoint created in dry-run mode is restarted from the beginning when used for a write dispatch; it cannot skip objects that were only planned. A write checkpoint resumes only in the same phase, table, and write mode. Immutable keys and conditional current-object writes make same-mode retries idempotent.
- `analysis-current` uses a numeric D1 rowid keyset cursor. Older checkpoints from the code-cursor implementation restart from the beginning and reset cumulative counters before resuming, so no rows are skipped. For the final delta, start that phase without a prior checkpoint so every current row is compared against R2. `analysis-history` and completed run logs use increasing IDs and can continue from their prior checkpoint. The legacy scheduled-run pointer is emitted only after the whole phase is complete; Worker health returns the newer of that migrated pointer and the live R2 analysis-run pointer.
- The D1-to-R2 workflow is manual only. It has no schedule, push/PR trigger, or deployment step. A single workflow concurrency group serializes all migration phases. The Worker CI tests the migration logic without production credentials.
- The workflow grants `contents: read` for checkout and `actions: read` for the read-only Environment, deployment-branch-policy, and prior-run artifact API calls. GitHub documents `Actions: read` for the Environment and branch-policy read endpoints; no additional write permission is needed for preflight. The workflow does not create deployments or grant Actions write. Environment protection still gates the migration job. See [Environment REST API permissions](https://docs.github.com/en/rest/deployments/environments), [branch-policy REST API permissions](https://docs.github.com/en/rest/deployments/branch-policies), and [workflow token permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
- The workflow job is restricted to `refs/heads/main`, and the migration job references the `d1-r2-migration` GitHub Environment. A separate preflight job checks that this environment already exists, has a required reviewer with self-review disabled, and permits only the `main` branch. It does not call the [environment-secrets listing endpoint](https://docs.github.com/en/rest/actions/secrets#list-environment-secrets): that endpoint requires the Environments repository permission, which is absent from the [available workflow `GITHUB_TOKEN` permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions). After the protected environment is approved, the migration job checks that all five required secret values are present without printing them, before any D1/R2 request. GitHub automatically creates a missing environment referenced by a workflow without protection rules or secrets, so the preflight must fail on a missing environment instead of allowing that implicit creation. Before storing migration credentials, a repository administrator must configure the environment to meet these rules. Store the dedicated credentials below only as environment secrets; do not create matching repository or organization secrets.
- A read-only browser inspection of `https://github.com/masacgt/Diview/settings/environments` at 2026-11-03 20:38 UTC showed only the `IRBANK_API_KEY` Environment; `d1-r2-migration` is absent. No secret values were read and no settings were changed. The migration workflow has not been run. Create and verify the protected Environment before storing migration credentials or dispatching the workflow.
- `workflow_dispatch` can be run against a branch other than the default branch, and the selected ref supplies the workflow revision. The shell-level ref check is defense in depth; the protected Environment is the boundary that prevents a changed branch workflow from receiving migration credentials. No workflow run is part of this task.
- A resume run checks that the supplied run ID belongs to this repository's completed `workflow_dispatch` run of this migration workflow on `main` before downloading its checkpoint artifact. The migration tool then checks the checkpoint phase, table, and hashes.

1. Before any D1 SQL, the workflow queries account-wide UTC-day usage with the separate Analytics Read token. The CLI repeats that check immediately before each phase opens its D1 client. ### Durable Object rate-limit cutover gate

Every active public `GET /api/v1/*` data route is subject to its route-specific Durable Object bucket unless it has a more restrictive explicit limit (for example, the J-Quants daily quote route). Legacy device-managed routes return `410` before rate limiting and do not read D1 or R2; feedback has its own write limit. R2-backed search, catalog, quote, security, financial, analysis, history, and health reads are not exempt because they avoid D1. The Worker regression test covers the default 300 requests per 60 seconds, HTTP 429, `Retry-After`, and no D1 calls for the previously exempt routes. The DO's one-time legacy D1 seed lookup remains a separate cutover behavior.

Use the temporary D1 write fence in `operations/rate-limit-handoff-fence.sql` as the cutover barrier. It creates `BEFORE INSERT`, `BEFORE UPDATE`, and `BEFORE DELETE` triggers on `api_request_log` that abort legacy mutations while leaving the DO's one-time `SELECT` import available. The legacy limiter is one atomic UPSERT statement. Since each D1 database processes queries one at a time, an UPSERT committed before the fence is visible to the later DO import; one executed after the fence is rejected. This is the ordering guarantee needed to avoid a fixed sleep or an unobservable request-drain assumption. D1's single-threaded query processing and its sequential batch semantics are documented in [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) and the [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/). D1 supports most SQLite SQL conventions; existing project migrations also use `RAISE(ABORT, ...)` triggers. Verify the exact fence SQL against a disposable D1 database before production use.

### Bounded D1 counter import

#### Runtime requirements

`RATE_LIMITER_D1_FENCE_AT` and `RATE_LIMITER_D1_IMPORT_UNTIL` are Unix epoch seconds supplied as Wrangler plain-text vars on every bridge and final Worker deployment. They are intentionally absent from `wrangler.toml` because their values are created at cutover. Therefore every later deploy or bridge rollback must also pass the exact pair from the handoff record; a bare `wrangler deploy` drops the values and makes each valid DO rate-limit request fail closed while D1 remains bound. The README deploy command prompts for the recorded pair. The fence timestamp is captured only after all three D1 fence triggers have been read back. Re-read the active backend configuration immediately before cutover; the currently verified limiter window is 60 seconds. Choose the cutoff no earlier than the fence timestamp plus the maximum active window and a 60-second safety margin. The Worker validates that the cutoff covers at least its current configured window. It fails closed if either var is missing/malformed, the fence timestamp is in the future, or the interval is too short.

After verifying the fence, calculate and retain one pair of values. Pass the exact same values to the bridge, final R2/DO Worker, and any bridge rollback. This bounds first-use D1 imports; when the cutoff passes, new DO buckets start at count 1 without reading their expired legacy rows.

```powershell
$maxLimiterWindowSeconds = 60 # Re-read backend-config:v1 immediately before cutover.
$safetyMarginSeconds = 60
$rateLimiterD1FenceAt = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
$rateLimiterD1ImportUntil = $rateLimiterD1FenceAt + $maxLimiterWindowSeconds + $safetyMarginSeconds
npx wrangler deploy --config wrangler.cutover-paused.toml --var "RATE_LIMITER_D1_FENCE_AT:$rateLimiterD1FenceAt" --var "RATE_LIMITER_D1_IMPORT_UNTIL:$rateLimiterD1ImportUntil"
```

Use the same `--var` arguments with the final Worker configuration. If the final deploy or a later rollback occurs after the saved deadline, keep the original timestamps: the Worker skips D1 imports because every pre-fence counter window has expired. Recalculate neither timestamp after the bridge starts serving traffic.
